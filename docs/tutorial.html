把一堆中转站账号，接进 CPA 的多上游轮询

粘贴 url,key → 四段各打一次真实请求定归属 → 读现有档位谱给出 不挡在用站的 priority → diff 确认 → 行级写回 config.yaml（保注释）→ 触发 CPA 重载 → 端到端验证。
这份教程讲的是每一步为什么这么设计 —— 每条判定背后都是一次实测 误判的修正。

01

全景：一次导入经过什么

六个阶段，每个阶段都可以停下来看结果再决定要不要往下走。

为什么不做「全自动导入」

探测只能证明此刻这一次请求成功了。它证明不了余额够用、限流 阈值、长时间稳定性、深夜是否降级。而写进 config.yaml 的 priority 一旦过高，会让已经跑了两夜、证明过自己的站 一次都不被尝试。所以定档默认走试用期，且写回前必须人看一眼 diff。

02

段决定形态：url 带不带 /v1 都行

同一个域名在四个段里的 base-url 形态与请求路径都不同。 用户不必记 —— 解析时按目标段自动规范化。

段base-url 形态请求路径鉴权头
gemini-api-key裸域名 /v1beta/models/{model}:generateContent?key= 查询串
claude-api-key裸域名 /v1/messages Bearer + x-api-key + anthropic-version
codex-api-key带 /v1 /responsesBearer
openai-compatibility带 /v1 /chat/completionsBearer

解析时做的四件事

裸域名自动补 https
  • x.example → https://x.example
  • 形态无法识别的行进「无效」清单，不静默丢弃
剥尾部 /v1，但不误剥 /v1beta
  • /v1beta 是 gemini 的真实路径段
  • 剥掉它请求必然 404
主机名统一小写
  • 大小写不同不该算两台机器
  • 否则同站两种拼写各探一遍，白烧配额
Key 一律脱敏后展示
  • 前 6 后 4，中间省略
  • 短 Key 只留前 2 位
踩过的坑：剥协议的正则忘了忽略大小写

取主机名的实现是「剥掉 ^https?:// 再取第一段」。这个正则 不带 re.I 时，HTTPS://x.example 剥不掉， 取出来的主机名是 HTTPS: ——

于是任意两个用大写 scheme 粘贴的站，会撞进同一个形态缓存键。 第二个站直接套用第一个站学到的模型清单、代理、必需头，然后写进 config.yaml。这不是浪费配额，是写错配置。

03

四阶段探测

每一阶段问的是不同的问题，前一阶段的结论决定后一阶段要不要跑。

04

定性九类：正文关键词优先于状态码

同一个 403 可能是三件完全不同的事，处置方向相反。 只看状态码必然误判。

类别典型码判据处置降权
余额403/402 正文含额度 / quota 字样充值即自愈否
IP封403 Cloudflare 特征词换出口 IP是
边缘403 正文为空重试即可否
门禁403 有正文但无上述特征站方策略是
反测活400 命中测活探针关键词换探测载荷否
限频429 bulk probing detected降并发否
死路400/404/500 model_not_found / 无可用渠道不接入是
鉴权401 unauthorizedKey 无效是
临时500/503 upstream busy稍后重试否
判定顺序本身就是一条实测教训

余额判定必须排在 Cloudflare 判定之前。 有个站的 403 正文是 「预扣费额度失败, 剩余 $0.19」—— 那是余额不足，不是门禁。而同一条正文里 可能同时出现 CF 的 cdn-cgi 字样。

判错的代价是处置方向完全相反：一个该充值，一个该换 IP。 按 CF 判就会把一个充钱就能用的站永久降权。

「降权」与「不可接入」是两个独立判断

余额不足 → 可接入（充值自愈）、不降权。限流 → 可接入（CPA 自带轮换）、 不降权。403 空正文 → 概率性边缘拦截，不代表站点坏，不降权。
只有死路 / IP封 / 鉴权 / 门禁这四类才真正降权。

HTTP 200 也不等于可用

有的中转站对所有请求都回 200，把真实错误放在正文里。 工具因此要检查正文顶层有没有 error 结构（或顶层 "type":"error"）—— 命中就不收该模型。

为什么这条比判死更危险

「是不是 200」只看状态码，而换模判定在拿不到 model 字段时 按设计放行（无证据不判换模）。两者叠加，这种站曾被判成 四段全可用、注册 11 个模型，而它完全不能用。

死站进了 config.yaml 会把 request-retry × max-retry-credentials 的尝试预算吃光， 最终客户端收到 500 —— 判死只是白丢一个站，判活会拖垮整个轮询池。

判据刻意窄：空值 null/""/{}/[] 不算，非 JSON 不算，嵌在 choices/candidates/content 里的 error 字样不算 —— 模型正常输出完全可能谈论 error。

临时错误要重试，一个不存在的模型不能判死整段

503 / 502 / 504 重试一次
  • 站方负载上限不代表站点不可用
  • 持续 503 判「临时」而非「死路」，重试有上限
全部种子失败时取最严重的类别
  • 不是取最后一个种子的结论
  • 种子模型是工具写死的猜测，它不存在不能说明站不可用

实测过的失败链：某站 claude-opus-5 返回 503（站方忙）、 claude-sonnet-5 返回 404（该站根本没这个模型）—— 原来整段判「死路」。而 sonnet-5 只是种子列表里的第二个名字。

404 model_not_found 属于模型专属死路，换个模型继续试； 敏感词、分组无渠道这类与模型无关的死路才立即收敛以省请求数。

04.5

客户端门禁与画像系统

同一站、同一 Key，探测 503 门禁、真实 Claude Code 207 次成功 —— 成败取决于下游客户端发的头。

为什么需要画像

中转站按客户端身份门禁。实测 2026-08-31：

谁在调用 CPA下游发的头zzzcoding 结果
日常用的 Claude Code完整 CC 头集207 次成功
CPAMP 测试按钮只有 x-api-key + content-type503 门禁
自写脚本 / 其他工具各自的头看运气

CPA config 条目 fingerprint-profile 空白时， preserveCallerFingerprint = true（claude_executor_request.go:755）， 做的是 copyClaudeCallerFingerprintHeaders —— 透传下游客户端的头， 缺 UA 才补 CLIProxyAPI/<版本>。门禁成败外包给了下游。

25 档画像梯 × 4 段

按客户端族分组（cc / codex / gemini-cli / openai-sdk / browser），族内嵌套超集。 baseline 失败后逐档升级，第一个通的即最小必需画像。

段梯子（部分）
claudebaseline → cc-min → cc-std → cc-full → cc-body-json → browser-ua
codexbaseline → originator-only → codex-tui → codex-full → browser-ua
geminibaseline → gemini-cli → gemini-cli-full → browser-ua
compatbaseline → openai-sdk → cc-min → cc-std → cc-full → cc-body-json → browser-ua

超集不是平行尝试 —— agentrouter 的门票是 user-agent + anthropic-beta + x-app 三项缺一不可。 如果梯子是「试 A、试 B、试 C」，三项各试一遍全败，而它们的并集本来是通的。 改成超集后，第 k 档失败即前 k 档的并集都不够，不必回头补试。

headers + body_patch 双层

metadata.user_id 是请求体字段，旧 identity_combos 只返回 headers 表达不了。新 Profile 同时给 headers 与 body 补丁：

画像headersbody_patch
cc-minuser-agent + anthropic-betametadata.user_id（JSON 形态）
cc-std+ x-app + Anthropic-Dangerous-…同上
cc-full+ X-Stainless 全族 + session id+ system 标记块 + stream

模板变量 {key_hash} / {uuid1..3} 按 Key 与请求求值 —— 静态 user_id 会让所有 Key 共用一个假身份，站方一眼看穿。

实测依据（13 站 claude 段）

站baseline 结果最小必需画像
10 站200 可用无需画像
agentrouter401 unauthorized clientcc-std（三个头）
zzzcoding503 only allows CC clientscc-std + fingerprint-profile

画像写进 config.yaml 条目 headers（四段通用、与下游客户端无关、优先级最高）。 fingerprint-profile 只在站方要请求体字段时用（目前 13 站里只有 zzzcoding 一个）。

两个新类：时段与 WAF

时段类（usable=True）

分组按窗口开放。实测 hybgzs codex 段 09:00~18:00 —— 窗口外打凭据有效但站方拒绝，报 403 + 提示「限时段」；窗口内可用。

立即收敛（不重试），导入时标注窗口并提示手工复测。

WAF 类（usable=False）

站方 WAF 按形态拦。实测 hybgzs 三段带代理仍被拦 访问已被拦截 —— 换 IP 无效，不是封 IP，是请求形态问题。

报告提示调整画像 / User-Agent，或放弃该站。

05

静默换模：比不可用更危险

站方照常计费，却返回另一个模型。HTTP 200，一路绿灯。

为什么响应 id 比 model 字段可靠

上游能随手改 model 字段的值，改不了 id 的生成方式。

id 形态推断的真实后端
msg_bdrk_…AWS Bedrock
msg_01 + base58（排除 0OIl）Anthropic 官方
msg_ + 32 位 hex中转自造
chatcmpl-…OpenAI Chat 兼容，多为中转
resp_ + 40 位以上 hexOpenAI Responses 官方形态

宽松匹配的边界在哪

model_matches(requested, actual) 要放行合法的版本差异， 又要抓住降级。两个方向都容易做错：

必须放行
  • actual 为空 —— 无证据不判换模
  • 纯数字日期后缀：-20260101、-0827
  • 能力开关：-thinking、-latest
必须判换模
  • 档位降级：-mini、-lite、-haiku
  • 带字母的实验后缀：-exp-0827
  • 凑巧共享前缀的不同族：gpt-4 vs gpt-40
两个方向都真的踩过

放行过头：为兼容日期后缀写了裸 startswith，结果把 gemini-2.5-flash → gemini-2.5-flash-lite 也判成同一模型。 站方拿 lite 冒充 flash 照常计费，探测一路绿灯，条目被写进配置。

抓得过头：更早的版本在 actual 为空时返回「换模」。 真因是响应读取被截断 —— Codex 的 /v1/responses 把 40KB+ 的 系统提示放在前面，model 字段排其后被切掉。结果是 100% 假换模率。所以现在的规则是：无证据不判换模。

截断校验：200 不代表真吃下了那么多

发出 105 万字符，上游回 200 且报 input_tokens: 132696 —— 重复字符实测约 1 char/token，这个数字远小于发送量，说明上下文被截断了。 低于 50% 即视为截断，那个 200 不可信。

06

定档：这是整个工具最容易做错的部分

CPA 按 priority 分层隔离。插进去不只是「排序靠前一点」。

三条硬约束

1 · 不动任何现有值
  • 只在空档里插
  • 现有条目的 priority 一个字节都不改
2 · 不劫持顶层
  • 天花板取该候选所有声明模型现有顶层的 min
  • 取 max 就会漏掉：同时声明 opus（顶层 1000）与 sonnet（顶层 120）时， 插 975 不动 opus，却把 sonnet 的顶层整个换掉
3 · 试用期默认
  • 新站进最低可插档，不按分数抢高档
  • 分数变成理由里的「稳定运行后可提到 N」
  • --by-score 才按分数一步到位
影响面按模型分别计算
  • 同一站的不同模型可能处在不同档位
  • 算一次「站的影响」会漏掉一半
试用期为什么是默认：一个实测出来的代价

一个刚探测完、零运行历史的新站，在 claude 段按分数会拿到 975 —— 挡住 6 个已经跑了两夜、证明过自己的站。那 6 个站只在新站也不可用时 才被尝试，等于用未知替换已知。

哪些站「挡住它零代价」

下层站不是等权的。有两个健康度信号说明「挡住它没有任何损失」：

weight: 0 —— 强信号
  • CPA 的选择器已经把零权重凭据整个剔除
  • 它本来就不会被选中
  • 同一站多个 Key 时，全部为 0 才算整站死掉
注释里的实测结论 —— 弱信号
  • # xxx：实测 503 No available channel
  • 注释可能过期，所以只用于降低挡住它的代价
  • 绝不用它直接排除任何站
站名与域名不保证有公共子串

注释里写的是人读短名，配置里是域名。一个叫 SwiftRelay 的站 可以住在 api.swiftly.example —— 两者没有公共子串。

所以别名表必须从 openai-compatibility 段的 name 字段建（那是文件里唯一权威的对应关系），而不是靠字符串猜。 早期版本用「短名是域名的某个点分标签」来匹配，那个站因此静默漏判 —— 实测 503 的结论对定档完全失效，不报错，只让定档悄悄变保守。

反过来也不能做前缀匹配：aliyuncs 会被短名 aliyun 命中，把两个不同的站判成同一个。误判方向是 把活站当死站，后果是新站拿到过高档位 —— 比漏判严重得多。 所以宁可漏，不可错；匹配不上的短名会被记进 unmatched_notes 显示给你，让漏判可见。

06.5

前缀规整：站级前缀 + 段级别名

62 个 claude 条目都是 ANT、13 个 compat provider 都是 CHMA —— 「指名某站」这个能力事实上不存在。

现状的问题

rewriteModelForAuth（conductor_models.go:685-698）只判 「模型名是否以这个 prefix 开头」，不判「是哪个站的 prefix」。所以 ANT/claude-opus-5 同时命中全部 12 个 claude 站， 落到哪个由 priority + 加权轮询决定。

你以为的实际行为
调 ANT/claude-opus-5 指名某站同时命中 12 站，轮询
调 CHMA/gpt-5.6-sol 指名某站同时命中 13 站，轮询

这不是 bug，是 prefix 的语义（namespace，不是唯一键）。但「叫得出某个站」是运维必需的 —— 单点测试、复现问题、定向清缓存都要它。

两层前缀：站级独占 + 段级别名

14 站各自独占前缀（从域名生成，agentrouter → AGR、kktoken → KKT）， 保留原名轮询，用 models[].alias 补段级兼容名。

你想要的用哪个名字效果
让 CPA 自动挑最好的站claude-opus-5（原名）按 priority 轮询全部 12 站
指名 agentrouterAGR/claude-opus-5只落 agentrouter 那 7 条
指名 kktokenKKT/claude-opus-5只落 kktoken 那 5 条
兼容旧客户端（用 ANT/...）ANT/claude-opus-5（别名）同原名轮询

三个名字同一条链路、同一套 headers、同一个成功率。原名一直在， 不会因为改 prefix 而消失 —— applyModelPrefixes （service_models.go:576-616）的 forceModelPrefix 判断保证了这点。

域名前缀说明

api.zzzcoding.orgZZZ沿用你手工定的值

N123 / N100 前面那个 N 是必需的：数字开头的模型名 在部分客户端里会被当数值解析。规则写死在代码里，同一个域名永远得到同一个前缀（幂等）。 撞车时加序号。你手工定的值会被尊重，工具不动。

段级别名可选

补 models[].alias: ANT/<原名> 会让每个模型多一行， config.yaml 明显变长。119 个条目里模型数最多的是 chiangma compat 段（64 个模型）， 那一个 provider 就多 64 行。

这是保留 ANT/xxx 可用性的必然代价。 --keep-section-prefix 开关控制要不要补。 如果确认没有客户端在用 ANT/... 这类名字，可以关掉，config 保持干净。

为什么段级别名必须走 alias 而不是 prefix

一个条目的 prefix 字段只能填一个值，站级占用了它。 CPA 的 compileAPIKeyModelAliasForModels （conductor_models.go:656-682）会把 alias 与 name 双向注册进查表， 所以 ANT/xxx 照样能命中。

07

写回：行级编辑，保注释

不用 yaml.dump —— 那会把配置里几百条排障注释全部丢掉。

那些注释是「哪个站什么时候为什么被降权」的唯一记录，而定档逻辑 本身还要读它们。所以流程是：读原文 → 按行插入 → 写原文。

写回一个条目的形状（字段顺序与现有文件一致，diff 看起来像手写）
  # 2026-08-31 批量导入 · 得分 100 · 试用期档位 465
  - api-key: "sk-…"
    base-url: "https://relay-x.example"
    prefix: "ANT"
    priority: 465
    models:
      - name: "claude-opus-5"
        alias: "claude-opus-5"
        max-context-length: 200000   # 实测值

四个容易做错的细节

缩进不猜，从现有条目读
  • 四段的缩进未必一致
  • 猜错整段结构就变形
max-context-length 只写在实测过的那个模型上
  • 同站不同模型的窗口能差一个数量级
  • 把 opus 的实测值抄给 haiku，客户端会按错的窗口定压缩点 —— 那正是这个字段要治的 400
prefix 沿用该段主导值
  • 它是额外加一个别名，不取代原名
  • 缺它不会让站不可用，但按 ANT/xxx 发的请求命中不到新站
compat 段按站归并
  • 一个 provider = 一个站，多个 Key 挂在 api-key-entries 下
  • 每个 Key 生成一个同名 provider 会让模型清单重复 N 遍
段尾在哪：一个不报错的静默错位

这份配置的写法是「下一段的说明注释写在下一段段头之前」。于是 gemini 段末尾挂着 32 行属于 codex 的说明、codex 段末尾挂着 89 行属于 claude 的说明。

如果段尾只回退空行、不回退注释，新条目就插到那些注释后面 —— 结果 codex 的整段文档注释跑到 gemini 的新条目上面去了。YAML 仍然合法 （段头还没出现，条目确实还在上一段里），所以不报错、不失败， 只是把注释归属悄悄搞乱。

值里的控制字符：能凭空多出一个段

标量转 YAML 字面量时，只处理引号是不够的。三种输入各有各的破法：

· 以单个反斜杠结尾 → 闭合引号被转义掉，整个文件变成非法 YAML。
· 含反斜杠 + n → YAML 读成真换行，Key 静默变质（长度都变了）。
· 含真换行 → 写出的行断成两截。YAML 仍解析成功，但段定位是逐行 正则扫描，会把折出来的半行当成真段头 —— 实测能凭空多出一个 openai-compatibility: 段，下一次写入插进错误位置。

所以控制字符必须在这一层一次性转义掉，保证一个标量只占一个物理行。

07.5

全量重探：把既有站也一起重新定档

上一章的行级插入不动既有条目一个字节。这一章讲的是相反的选择， 以及为什么它需要一个勾选框而不是默认行为。

行级插入修不了的那类问题

只探新站是安全的默认值。但有四类问题它碰不到：

headers 过期
  • 站方改了门禁，原来那套标识头不再管用
  • 从 config.yaml 看不出来，要看实测响应
priority 错位
  • 多次插档之后，能用的站被压在死站后面
  • 数值本身没错，是相对关系错了
代理已失效
  • proxy-url 指的出口不通了
  • 每次轮到这条都白等一次超时
模型清单陈旧
  • 站方新开了模型，或下掉了原来声明的
  • 写着的模型 CPA 路由过去必然失败

四类的共同表现都是成功率下降，而共同的诊断手段都是重新打一次。

为什么是勾选框，不是默认行为

重探会把此刻正在维护的站判成不可用

探测拿到的是「这一刻站方返回什么」，不等于「这个站正确的配置是什么」。 某站此刻余额不足、限流、临时维护，重探都会判它不可用——如果这时直接 写回，明天它恢复了但配置已经被改掉。

所以决定权在操作员：工具负责把现状探清楚、给出完整 diff， 由人判断哪些改动该接受。

先去重：条目数不等于要探几次

config.yaml 的条目是「(凭据, 段)」的组合。很多中转站用同一把 Key 提供多种协议，于是同一个 url+key 被写进 2-4 个段。

实测那份生产配置：175 个条目只有 77 个不同凭据

9 个凭据跨全四段、11 个跨三段、49 个跨两段。而探测的语义本来就是 「拿一个凭据把四段各打一遍」—— 按条目喂它等于同一个凭据重复探 2-4 次， 白打 98 次全流程。

去重键取 (host, api_key) 而不是 (base_url, api_key)： 同一个站在不同段的 base-url 形态不同（codex/compat 带 /v1， 另两段不带），用后者会把同一个凭据判成两个。

再省画像：门票是站+段的属性，与模型无关

画像梯的调用点在种子模型循环内部：第一个种子全败后，循环走到下一个 种子，整梯重跑。而每段有 2-3 个种子 —— claude 段 7 档 × 2、compat 6 档 × 3。

但站方查的是 headers 与 body 形态，不看模型名。所以第一个种子试完 整梯全败之后，同段的后续种子在问同一个问题。假上游实测（全 403，复现 那个「只允许 CC 客户端」的站）：

优化前 57 次   browser-ua 打了 9 次、cc-min/cc-std/cc-full 各 5 次
优化后 30 次   每档恰好 1 次
为什么不能把画像梯改成二分

梯子是嵌套超集，二分找到的是「某个能通的档」而不是「最省档」。 找到 cc-full 就停会多写 5 个无用 header 进 config.yaml， 站方改门禁时更容易整体失效 —— 那正好破坏「找最小必需集」这个设计意图。

并发模型：放大吞吐，不放松限频

去重加省画像之后，单凭据四段全不通约 30 次请求。77 个凭据串行跑仍要 半小时，所以站级并发是必须的。

并发数不是写死的：读 cgroup 算出来

容器里 os.cpu_count() 返回宿主机核数

64 核宿主上跑 --cpus=4 的容器，它仍然报 64 —— 按它算并发 会超配 16 倍。所以要读 cgroup：v2 的 cpu.max / memory.max、v1 的 cfs_quota_us / limit_in_bytes。

推荐值 = min(核数 × 12, 可用内存一半 ÷ 12MB, 上界 64)。docker 实测五档：

容器规格推荐并发受限于
--cpus=0.5 --memory=256m6核数
--cpus=1 --memory=512m12核数
--cpus=2 --memory=1g24核数
--cpus=4 --memory=24g48核数
--cpus=8 --memory=2g64内存 85 与上界 64

界面把完整依据摊开显示（4.0 核 × 12 = 48 · 24576MB 的一半 ÷ 12MB = 1024 → 取 48（受限于核数））—— 一个凭空出现的数字，操作员没法 判断该不该改。

三项优化叠加的实测收益

优化前优化后省
待探测单元175 条目77 凭据56%
单凭据请求数57 次30 次47%
总请求数（最坏）9,9752,31077%
48 并发耗时3.9 分钟0.9 分钟4.3×

注释保全：两种写法，两种做法

上一章的行级插入保注释靠的是不碰它们。全量重写做不到这一点—— 所有条目都要重新渲染，注释必须主动挂回去。

行级插入（增量）
  • 只在段尾追加
  • 既有的每一行原地不动
  • 注释自然保住
全量重写（重探）
  • 条目全部重新渲染
  • 按 (段, name/base-url) 给注释建索引
  • 渲染条目时按索引挂回去

全局配置（host/port/tls/remote-management 那些）按「第一个 *-api-key 段之前」整段原样保留，不参与重建。

文件里的排序与 CPA 的优先级方向相反

重建后的条目按 priority 降序排列，而 CPA 侧的语义是 数值小的优先（scheduler.go:1085 升序排序）。所以文件里 排在前面的是数值大的、也就是优先级低的。

这个顺序只影响阅读，不影响 CPA 的选择——它按数值排，不按文件位置。

写回链一步没少

全量重写用的是同一条写回链：基线比对（被改过就 409）→ YAML 校验 → 写前备份 → 就地 O_TRUNC 覆写 → PUT 触发重载 → 端到端验证。

与 CPA-Manager-Plus 的并发写

CPAMP 走 CPA 的 PUT /config.yaml 做全量重写。本工具的基线比对 能挡住「在生成方案之后被改过」，但挡不住同一秒的并发。全量重探要跑几分钟， 这期间不要在 CPAMP 里改配置。

如实说明：还没对真实站跑过

全量重探目前只在假上游、7 项单元测试和一次端到端演练上验证过，没有对 175 个真实站跑过 一次完整流程。第一次实跑建议看完 diff 再决定是否写回。

08

生效链：写完盘不等于生效

这一段全是容器与文件系统的细节，但每一条都决定「改了却没生效」。

备份文件名撞名 = 把唯一的退路弄丢

备份名只到秒、且复制时撞名直接静默覆盖时：同一秒内写两次 （并发写回、脚本连续跑），第二次的备份会把第一次的覆盖掉 —— 留下来的是「第一次写完之后」的状态，真正的原始文件没了。

而就地覆写本身不原子、失败不回滚，备份是唯一的回滚手段。 所以撞名不是「多留一份少留一份」的问题。

并发写回：两个请求都以为自己拿的是最新基线

服务跑在多线程 HTTP 服务器上。「读文件 → 比对基线 → 校验 → 写盘」 这四步之间没有互斥时，两个并发的写回请求会各自比对到同一份 未改动的基线、双双通过，然后依次写盘 —— 后写的覆盖掉前一次的全部改动， 而给前一个客户端回的仍是 200。

顺序执行不会有这个问题（第二次的基线比对会正确地报 409）， 所以顺序跑的测试抓不到它。修法是把那四步整段放进一把锁。

排障：导出 CPA 的错误日志

要把日志发给别人看时，用项目自带的 tools/export-logs.sh，别手动 tar：

在 config.yaml 所在目录执行；默认取最近 50 个错误日志
cd /opt/deploy
bash upstream-importer/tools/export-logs.sh
错误日志含明文上游 API Key

CPA 在 debug: true 下把完整请求体写进错误日志， 其中有 Authorization 头。手动打包发出去，那些 Key 就跟着走了。

脚本默认脱敏，覆盖 6 种凭据形态；改的是副本，原始日志一个字节都不动， 并且脱敏后会自证一遍 —— 仍检出凭据就拒绝打包。上游 URL、状态码、错误消息 都保留，排障信息不受影响。

包里的 digest.txt 是摘要表，一行一个错误日志， 先看它再决定翻哪几份原文 —— 单份原文可达 2MB。其中「尝试」列为 0 意味着 CPA 在选择阶段就返回 503、请求根本没出门； 大于 0 才是真的发到了上游。两者的处置方向完全不同。

两类日志不在同一个地方

error-logs-max-files 故障持续爆发时可回看说明
50约 6 小时 一次故障就能打满 10 个，75 分钟内被挤出（实测）
200约 25 小时 推荐值；平稳期错误稀少，可能覆盖数天
调 logs-max-total-size-mb 不会延长保留时间

只有错误日志时永远是文件数先撞闸门：最坏情况 200 × 2.1MB ≈ 420MB， 连 512MB 都到不了。那个总量参数在这个场景下只是兜底。

而且 CPA 的清理机制设计目标是「防止撑爆磁盘」，不是「长期保存」。 真要留全量就定期归档出去 —— 导出的包已脱敏，可以直接往别处搬。

cron 每天归档一次，攒多久都不怕被挤掉
30 4 * * * cd /opt/deploy && bash upstream-importer/tools/export-logs.sh 200 >/dev/null

更多（两类日志的完整对照、为什么不要开 request-log） 见 README 的「导出 CPA 错误日志」一节。

站方不给测活怎么办：人工接管

有些站探针式短消息会被拦，或分组只允许特定客户端 （This group is restricted to Claude Code clients），而真实对话 完全正常。这类站探测必然判死，但它确实可用。

结果表里判死的那一行也有勾选框，右侧多一个模型输入框：

填了模型名（逗号分隔）才能勾上
写入  段      判定    处置                        模型（手填）
 ☐   claude  门禁   403 且无余额/CF 特征   [claude-opus-5, claude-opus-4-8]

为什么必须手填：探测没验成功过任何模型，工具无从推断该注册什么。 模型清空会同步取消勾选 —— 避免「看着会写入、实际不写」的错觉。

人工接管只绕过「能不能用」这一个判定

去重、定档、影响面计算、diff 确认一道都不少 —— 那几道防的是写坏 config.yaml，与「这个站能不能用」是两件事。

试用期策略照常生效，影响面按你给的模型清单实算而不是恒为 0。 方案里会标注「人工接管（探测判「门禁」）」并附上警告， 事后能看出这条是怎么进来的。

工具不会验证你填的模型名

写错会让 CPA 每次轮到它都失败，消耗重试预算。填之前先在站方后台 或用 /v1/models 确认。命令行侧目前没有等价参数，要人工接管请用网页。

三条红线

服务只绑 127.0.0.1
  • 强制 Bearer token，没有免鉴权模式
  • 对外必须经 nginx 加 TLS + IP 白名单
  • 别加 basic auth —— 它与前端的 Bearer 抢同一个头
job 状态只在内存
  • 刻意不落库：持久化等于把明文 Key 写到磁盘
  • 代价是重启丢失进行中的任务与方案 id
写回前必看 diff
  • 它改的是被多个容器 bind mount 的生产配置
  • 换模站、劫持顶层的候选默认不勾选
config.yaml 绝不进仓库
  • 含明文上游 Key 与管理密钥哈希
  • 一旦推上公开仓库，那些 Key 必须视为已泄露并全部轮换
10

发布：CI 与镜像

GHCR 零配置；Docker Hub 配三项，不配就安静跳过。

名称放哪必填说明
DOCKERHUB_USERNAMEVariables 是 用户名，同时是「要不要发 Docker Hub」的开关
DOCKERHUB_IMAGEVariables 可选 镜像名。留空 = 用 GitHub 仓库名
DOCKERHUB_TOKENSecrets 是 Access Token，权限 Read & Write 即够
用户名放 Variables，token 放 Secrets —— 不能颠倒

Variables 在构建日志里是明文；Secrets 会被 Actions 自动打码。 把 token 放进 Variables 等于把它印在每一次构建日志上。

另外：两项必填都要有才会发布。只设用户名、稍后再加 token 是很 自然的操作顺序，而那样会让每次构建都红在 401 上，且看不出是「token 还没配」。

secrets 上下文在 steps 的 if: 里不可用

官方的 Context availability 表里，jobs.<job_id>.steps.if 允许的是 github, needs, strategy, matrix, job, runner, env, vars, steps, inputs —— 没有 secrets。

写 if: secrets.X != '' 不报错，只是恒为空，那一步会 永远被跳过：「配好了却不发布」而且毫无提示，比直接失败更难查。 正确做法是在 job 级 env 里算一个旗标（那一层允许 secrets）， 步骤只看旗标。

发布前必做：隐去域名

要隐去的有两类，第二类最容易漏：

自有域名
  • 客户端入口、管理面板、本服务自身、自己作为上游时的域名
  • 同一域名四种角色，替换目标各不相同
第三方中转站域名
  • 它们是排障案例的主体
  • 公开出去等于公布「我在用这些站、它们各自什么毛病」
  • 散在 20 个文件里，比想象的多得多
替换脚本自己不能进仓库

这类脚本的规则表里必须逐条写着原始域名，否则认不出要替换什么。 也就是说脚本本身就是一份域名清单 —— 进了公开仓库等于把要隐去的东西直接 发出去。本项目实际踩过这一步：清理跑得很干净，却把清理器推上去了。

放仓库外，或让它从一个被 .gitignore 排除的规则文件里读。

替换后必须重跑测试 —— 占位符命名会影响断言数据
python3 tests/run.py                      # 必须仍全过
git status --short                        # 确认没有 config.yaml / .env
git ls-files | grep -iE 'scrub|domain'    # 清理器别在里面
占位符怎么取名会影响测试是否通过

这不是洁癖，是三条真实约束：

1 · 字母按原名字母序分配。有断言把运行时 sorted() 的结果和源码里的字面量比对，字母乱分配会让两边排序不一致 —— 测试失败， 而原因跟被测逻辑毫无关系。
2 · 短名 == 域名首标签。无别名表时的兜底匹配靠这个性质。
3 · 但有一对故意不共享子串。「必须靠别名表才认得」那条断言靠它。 只顾 2 不顾 3，那条断言就恒真而不再验证任何东西。

另外，测试里当作前缀误匹配反例的几个域名刻意不替换 —— 换成占位符后那条断言会恒真。

本教程与代码同仓库。命令与判定规则若与代码不一致，以代码为准 —— 代码里每条判定的注释都写明了它对应哪一次实测教训。

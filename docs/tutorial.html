01

全景：一次导入经过什么

六个阶段，每个阶段都可以停下来看结果再决定要不要往下走。

为什么不做「全自动导入」

探测只能证明此刻这一次请求成功了。它证明不了余额够用、限流 阈值、长时间稳定性、深夜是否降级。而写进 config.yaml 的 priority 一旦过高，会让已经跑了两夜、证明过自己的站 一次都不被尝试。所以定档默认走试用期，且写回前必须人看一眼 diff。

02

段决定形态：url 带不带 /v1 都行

同一个域名在四个段里的 base-url 形态与请求路径都不同。 用户不必记 —— 解析时按目标段自动规范化。

段base-url 形态请求路径鉴权头
gemini-api-key裸域名 /v1beta/models/{model}:generateContent?key= 查询串
claude-api-key裸域名 /v1/messages Bearer + x-api-key + anthropic-version
codex-api-key带 /v1 /responsesBearer
openai-compatibility带 /v1 /chat/completionsBearer

解析时做的四件事

裸域名自动补 https
  • x.example → https://x.example
  • 形态无法识别的行进「无效」清单，不静默丢弃
剥尾部 /v1，但不误剥 /v1beta
  • /v1beta 是 gemini 的真实路径段
  • 剥掉它请求必然 404
主机名统一小写
  • 大小写不同不该算两台机器
  • 否则同站两种拼写各探一遍，白烧配额
Key 一律脱敏后展示
  • 前 6 后 4，中间省略
  • 短 Key 只留前 2 位
踩过的坑：剥协议的正则忘了忽略大小写

取主机名的实现是「剥掉 ^https?:// 再取第一段」。这个正则 不带 re.I 时，HTTPS://x.example 剥不掉， 取出来的主机名是 HTTPS: ——

于是任意两个用大写 scheme 粘贴的站，会撞进同一个形态缓存键。 第二个站直接套用第一个站学到的模型清单、代理、必需头，然后写进 config.yaml。这不是浪费配额，是写错配置。

03

四阶段探测

每一阶段问的是不同的问题，前一阶段的结论决定后一阶段要不要跑。

探测发的请求不是「裸请求」：参数分三层

常见的疑问是「会不会因为代理或头没配对，把好站判死」。答案分三层看 —— 每层的取舍不同，而第一层是不给选择的。

第一层的每一条都是踩坑改出来的

· gemini 用头不用 ?key= —— 2026-09-01 实测：用 query string 时某站三种画像全部连接层失败（000），而用头能拉到几百个模型。 探测测的不是 CPA 真实走的那条路，于是把一个可用站判死。

· claude 两个鉴权头都发 —— 中转站实现不一，只发一个可能误判 401。

· claude URL 带 ?beta=true —— CPA 三条 claude 路径全都带。 原来不带的理由是「少一个变量」，但那让探测与真实转发形态不一致：站方按 query 参数分流时，探测通了而 CPA 不通，或反之。 对齐优先于减少变量 —— 探测要问的是「CPA 这样发通不通」。

段族过滤：56% 的请求原本是白发的

聚合站的 /models 目录把三族模型混在一起报。探测队列原样接收， 于是 gemini 段拿 claude-opus-4-6 去打 /v1beta/models/claude-opus-4-6:generateContent —— CPA 永远不会 这样发：段决定协议路径，模型必须是该协议下的模型。

请求次数 成功率500 占比
跨族435 / 773（56%）5.5% 240 次 = 55%
同族33824.6%0 次

决定性佐证是最后一列：跨族请求里 240 次返回 500，而同族一次都没有。 500 被判「临时」触发重试，79 凭据那轮日志里 666 次 500 的最大头就在这。

这不只是烧配额

反复拿协议不匹配的模型名轰炸，正是站方风控盯的形态 —— 比一句「你好」更可疑。 SECTION_FAMILY 闸让三个协议段只探本族；compat 段不设限，它走 /chat/completions，本身就是万能转发口。 过滤在探测队列、目录落盘、方案生成三处各做一次 —— 任一处漏了都会复现。

目录优先：先问站方，再动手打

原来的顺序是「拿写死的种子模型撞 → 撞不上判死」，而 /models 目录在阶段二，只在阶段一已经成功时才跑。等于从头到尾没问过站方 「你到底有什么」。

实测后果：45/79 个凭据判 0 段可用，其中 7 个的目录明明拿得到模型 （最多 199 个）。而 model-scan 阶段（用目录里的模型）成功 200 共 78 次， 模型名如 claude-opus-4-6、gpt-oss-120b —— 全都不在种子表里。

GET 目录比推理请求安全

多数站不计费、不计入调用统计、不触发风控。参考实现全都只这么做：CPAMP 的健康检查只发 GET 目录（全库无 POST 测活），CLIProxyAPI 自己完全不探 上游存活。这与「严禁 Hi / 你好 这类简单测活」同向 —— 能不发推理就不发。

gemini 段的 /v1beta/models 分页，最多翻 20 页（与 CPAMP 同一上限）。

前两行的后果具体：?key= 那种形态实测被一批站直接拒 （前端用头能拉到几百个模型、用 query 拿 000），所以 legacy 会把好站报成 坏站；而 "hi" 正是站方反测活规则最先拦的形态，有封号 风险。

定性九类：正文关键词优先于状态码

同一个 403 可能是三件完全不同的事，处置方向相反。 只看状态码必然误判。

类别典型码判据处置降权
余额403/402 正文含额度 / quota 字样充值即自愈否
IP封403 Cloudflare 特征词换出口 IP是
边缘403 正文为空重试即可否
门禁403 有正文但无上述特征站方策略是
反测活400 命中测活探针关键词换探测载荷否
限频429 bulk probing detected降并发否
死路400/404/500 model_not_found / 无可用渠道不接入是
鉴权401 unauthorizedKey 无效是
临时500/503 upstream busy稍后重试否
判定顺序本身就是一条实测教训

余额判定必须排在 Cloudflare 判定之前。 有个站的 403 正文是 「预扣费额度失败, 剩余 $0.19」—— 那是余额不足，不是门禁。而同一条正文里 可能同时出现 CF 的 cdn-cgi 字样。

判错的代价是处置方向完全相反：一个该充值，一个该换 IP。 按 CF 判就会把一个充钱就能用的站永久降权。

「降权」与「不可接入」是两个独立判断

余额不足 → 可接入（充值自愈）、不降权。限流 → 可接入（CPA 自带轮换）、 不降权。403 空正文 → 概率性边缘拦截，不代表站点坏，不降权。
只有死路 / IP封 / 鉴权 / 门禁这四类才真正降权。

HTTP 200 也不等于可用

有的中转站对所有请求都回 200，把真实错误放在正文里。 工具因此要检查正文顶层有没有 error 结构（或顶层 "type":"error"）—— 命中就不收该模型。

为什么这条比判死更危险

「是不是 200」只看状态码，而换模判定在拿不到 model 字段时 按设计放行（无证据不判换模）。两者叠加，这种站曾被判成 四段全可用、注册 11 个模型，而它完全不能用。

死站进了 config.yaml 会把 request-retry × max-retry-credentials 的尝试预算吃光， 最终客户端收到 500 —— 判死只是白丢一个站，判活会拖垮整个轮询池。

判据刻意窄：空值 null/""/{}/[] 不算，非 JSON 不算，嵌在 choices/candidates/content 里的 error 字样不算 —— 模型正常输出完全可能谈论 error。

临时错误要重试，一个不存在的模型不能判死整段

503 / 502 / 504 重试一次
  • 站方负载上限不代表站点不可用
  • 持续 503 判「临时」而非「死路」，重试有上限
全部种子失败时取最严重的类别
  • 不是取最后一个种子的结论
  • 种子模型是工具写死的猜测，它不存在不能说明站不可用

实测过的失败链：某站 claude-opus-5 返回 503（站方忙）、 claude-sonnet-5 返回 404（该站根本没这个模型）—— 原来整段判「死路」。而 sonnet-5 只是种子列表里的第二个名字。

404 model_not_found 属于模型专属死路，换个模型继续试； 敏感词、分组无渠道这类与模型无关的死路才立即收敛以省请求数。

05

静默换模：比不可用更危险

站方照常计费，却返回另一个模型。HTTP 200，一路绿灯。

为什么响应 id 比 model 字段可靠

上游能随手改 model 字段的值，改不了 id 的生成方式。

id 形态推断的真实后端
msg_bdrk_…AWS Bedrock
msg_01 + base58（排除 0OIl）Anthropic 官方
msg_ + 32 位 hex中转自造
chatcmpl-…OpenAI Chat 兼容，多为中转
resp_ + 40 位以上 hexOpenAI Responses 官方形态

宽松匹配的边界在哪

model_matches(requested, actual) 要放行合法的版本差异， 又要抓住降级。两个方向都容易做错：

必须放行
  • actual 为空 —— 无证据不判换模
  • 纯数字日期后缀：-20260101、-0827
  • 能力开关：-thinking、-latest
必须判换模
  • 档位降级：-mini、-lite、-haiku
  • 带字母的实验后缀：-exp-0827
  • 凑巧共享前缀的不同族：gpt-4 vs gpt-40
两个方向都真的踩过

放行过头：为兼容日期后缀写了裸 startswith，结果把 gemini-2.5-flash → gemini-2.5-flash-lite 也判成同一模型。 站方拿 lite 冒充 flash 照常计费，探测一路绿灯，条目被写进配置。

抓得过头：更早的版本在 actual 为空时返回「换模」。 真因是响应读取被截断 —— Codex 的 /v1/responses 把 40KB+ 的 系统提示放在前面，model 字段排其后被切掉。结果是 100% 假换模率。所以现在的规则是：无证据不判换模。

截断校验：200 不代表真吃下了那么多

发出 105 万字符，上游回 200 且报 input_tokens: 132696 —— 重复字符实测约 1 char/token，这个数字远小于发送量，说明上下文被截断了。 低于 50% 即视为截断，那个 200 不可信。

06

定档：这是整个工具最容易做错的部分

CPA 按 priority 分层隔离。插进去不只是「排序靠前一点」。

三条硬约束

1 · 不动任何现有值
  • 只在空档里插
  • 现有条目的 priority 一个字节都不改
2 · 不劫持顶层
  • 天花板取该候选所有声明模型现有顶层的 min
  • 取 max 就会漏掉：同时声明 opus（顶层 1000）与 sonnet（顶层 120）时， 插 975 不动 opus，却把 sonnet 的顶层整个换掉
3 · 试用期默认
  • 新站进最低可插档，不按分数抢高档
  • 分数变成理由里的「稳定运行后可提到 N」
  • --by-score 才按分数一步到位
影响面按模型分别计算
  • 同一站的不同模型可能处在不同档位
  • 算一次「站的影响」会漏掉一半
试用期为什么是默认：一个实测出来的代价

一个刚探测完、零运行历史的新站，在 claude 段按分数会拿到 975 —— 挡住 6 个已经跑了两夜、证明过自己的站。那 6 个站只在新站也不可用时 才被尝试，等于用未知替换已知。

哪些站「挡住它零代价」

下层站不是等权的。有两个健康度信号说明「挡住它没有任何损失」：

weight: 0 —— 强信号
  • CPA 的选择器已经把零权重凭据整个剔除
  • 它本来就不会被选中
  • 同一站多个 Key 时，全部为 0 才算整站死掉
注释里的实测结论 —— 弱信号
  • # xxx：实测 503 No available channel
  • 注释可能过期，所以只用于降低挡住它的代价
  • 绝不用它直接排除任何站
站名与域名不保证有公共子串

注释里写的是人读短名，配置里是域名。一个叫 SwiftRelay 的站 可以住在 api.swiftly.example —— 两者没有公共子串。

所以别名表必须从 openai-compatibility 段的 name 字段建（那是文件里唯一权威的对应关系），而不是靠字符串猜。 早期版本用「短名是域名的某个点分标签」来匹配，那个站因此静默漏判 —— 实测 503 的结论对定档完全失效，不报错，只让定档悄悄变保守。

反过来也不能做前缀匹配：aliyuncs 会被短名 aliyun 命中，把两个不同的站判成同一个。误判方向是 把活站当死站，后果是新站拿到过高档位 —— 比漏判严重得多。 所以宁可漏，不可错；匹配不上的短名会被记进 unmatched_notes 显示给你，让漏判可见。

硬隔离有两条例外（2026-09-05 核实）

「只取最高那一桶」这条判据是整个定档算法与影响面计算的基础， 所以它的例外必须写清。

例外触发条件 本部署当前
codex/xai + 下游 WS preferWebsocket=true 时从高到低扫，返回第一个含 ws 凭据的档（scheduler.go 的 highestReadyPriorityLocked，源码注释原话 "even if they are in a lower priority tier than HTTP-only credentials"） 是活的 —— WRR + session-affinity:false 走内建选择器 快路
session-affinity 选择器是 SessionAffinitySelector 时，交给它的候选是 全部档位（conductor_selection.go 的 availableAuthsForSelector）。不限段、不限 WS 不触发 —— 生产配置 session-affinity: false

第一条本工具已经会报警告。第二条目前只有文档 —— 它一旦打开，本工具对 「已绑定会话」的挡站计数就不成立（对「新会话」仍成立，因为冷启动绑定还是从 最高档开始）。

WS 那一路的两条边界一并记下：pickMixed 在多 provider 时一律传 preferWebsocket=false，只有单一 provider 时才生效；旧路的 preferCodexWebsocketAuths 是在已经收窄到最高档之后过滤， 不跨档 —— 跨档只发生在 scheduler 快路。

已被 CPA 排除在池外的条目不参与避让

build_band 原来只看 priority / models / weight，于是下面这些条目被当成在用站参与定档避让 —— 而 CPA 根本不会把请求路由到它们。

形态CPA 侧的判据
compat 的 disabled: true synthesizer/config.go 与 service_models.go 都是遇 Disabled 直接 continue —— 那个 provider 连 Auth 都不合成
任意段 excluded-models 含 * 那正是管理面板「停用一个 config 型凭据」的实现 （config_apikey_disable.go 的 configAPIKeyDisablePattern = "*"）。 applyExcludedModels 用通配把该凭据的模型全过滤掉， 清单空则 UnregisterClient
base-url 为空 门槛按段不同：codex 与 compat 只要 base-url 空就在加载期被删 （config_normalization.go，compat 那句的注释原文是 "treated as removed"）；gemini 与 claude 要 api-key 与 base-url 都空才删
compat 的 models 为空 registerCompat 走 UnregisterClient，而 scheduledAuthMeta.supportsModel 在 supportedModelSet 为空时对任何具名模型返回 false。 codex 段相反 —— 空 models 会回落 GetCodexProModels()，仍在池

实测后果（构造三站）：一个 disabled: true 的 provider 在 300 档且 声明 kimi-k3 → model_top['kimi-k3']=300 → 新站被压到 225， 而理由文案说「会挡 N 个在用站」—— 其中那一个不在调度池里。

生产配置里这四种形态都是 0 例，所以是补闸不是修事故。但最后两种的段间差异 必须分开写 —— 一视同仁会把 codex 段的正常条目误判成出池。

65 个 claude 条目都是 ANT、13 个 compat provider 都是 CHMA —— 「指名某站」这个能力事实上不存在。

现状的问题

07

写回：行级编辑，保注释

不用 yaml.dump —— 那会把配置里几百条排障注释全部丢掉。

那些注释是「哪个站什么时候为什么被降权」的唯一记录，而定档逻辑 本身还要读它们。所以流程是：读原文 → 按行插入 → 写原文。

写回一个条目的形状（字段顺序与现有文件一致，diff 看起来像手写）
  # 2026-08-31 批量导入 · 得分 100 · 试用期档位 465
  - api-key: "sk-…"
    base-url: "https://relay-x.example"
    prefix: "ANT"
    priority: 465
    models:
      - name: "claude-opus-5"
        alias: "claude-opus-5"
        max-context-length: 200000   # 实测值

四个容易做错的细节

缩进不猜，从现有条目读
  • 四段的缩进未必一致
  • 猜错整段结构就变形
max-context-length 逐模型各写自己的
  • 同站不同模型的窗口能差一个数量级
  • 把 opus 的实测值抄给 haiku，客户端会按错的窗口定压缩点 —— 那正是这个字段要治的 400
  • 优先级：本次实测 > 原值搬运 > 不写。原值那一档 2026-09-03 才补 —— 它在 models: 块内，carry 有意跳过那一块，而方案只带本次 实测的那一个，于是本次没探上下文时历史值全丢（实测 8 处）
prefix 逐条搬原值
  • 它是额外加一个别名，不取代原名
  • 缺它不会让站不可用，但按 ANT/xxx 发的请求命中不到
  • dominant_prefix 只给新条目猜默认值；既有条目 自己写的才是真的。搞混会抹掉 121/121 条目的 prefix
compat 的 provider name 搬原值
  • name 就是 CPA 的 provider 身份 —— util.OpenAICompatibleProviderKey(name) 写进 provider_key
  • 冷却、模型能力、执行路由三处都按它索引；用 host_of(base_url) 现编会让 12/13 个 provider 改名， 冷却状态与能力缓存全部作废
compat 段按站归并
  • 一个 provider = 一个站，多个 Key 挂在 api-key-entries 下
  • 每个 Key 生成一个同名 provider 会让模型清单重复 N 遍
段尾在哪：一个不报错的静默错位

这份配置的写法是「下一段的说明注释写在下一段段头之前」。于是 gemini 段末尾挂着 32 行属于 codex 的说明、codex 段末尾挂着 89 行属于 claude 的说明。

如果段尾只回退空行、不回退注释，新条目就插到那些注释后面 —— 结果 codex 的整段文档注释跑到 gemini 的新条目上面去了。YAML 仍然合法 （段头还没出现，条目确实还在上一段里），所以不报错、不失败， 只是把注释归属悄悄搞乱。

值里的控制字符：能凭空多出一个段

标量转 YAML 字面量时，只处理引号是不够的。三种输入各有各的破法：

· 以单个反斜杠结尾 → 闭合引号被转义掉，整个文件变成非法 YAML。
· 含反斜杠 + n → YAML 读成真换行，Key 静默变质（长度都变了）。
· 含真换行 → 写出的行断成两截。YAML 仍解析成功，但段定位是逐行 正则扫描，会把折出来的半行当成真段头 —— 实测能凭空多出一个 openai-compatibility: 段，下一次写入插进错误位置。

所以控制字符必须在这一层一次性转义掉，保证一个标量只占一个物理行。

07.5

全量重探：把既有站也一起重新定档

上一章的行级插入不动既有条目一个字节。这一章讲的是相反的选择， 以及为什么它需要一个勾选框而不是默认行为。

行级插入修不了的那类问题

只探新站是安全的默认值。但有四类问题它碰不到：

headers 过期
  • 站方改了门禁，原来那套标识头不再管用
  • 从 config.yaml 看不出来，要看实测响应
priority 错位
  • 多次插档之后，能用的站被压在死站后面
  • 数值本身没错，是相对关系错了
代理已失效
  • proxy-url 指的出口不通了
  • 每次轮到这条都白等一次超时
模型清单陈旧
  • 站方新开了模型，或下掉了原来声明的
  • 写着的模型 CPA 路由过去必然失败

四类的共同表现都是成功率下降，而共同的诊断手段都是重新打一次。

为什么是勾选框，不是默认行为

重探会把此刻正在维护的站判成不可用

探测拿到的是「这一刻站方返回什么」，不等于「这个站正确的配置是什么」。 某站此刻余额不足、限流、临时维护，重探都会判它不可用——如果这时直接 写回，明天它恢复了但配置已经被改掉。

所以决定权在操作员：工具负责把现状探清楚、给出完整 diff， 由人判断哪些改动该接受。

不加新账号也能跑

输入框留空、只勾「全量重探模式」，就是纯体检 —— 重新探测既有条目、 按结果更新配置，不新增任何站。config.yaml 用久了想知道哪些站还能用、 哪些 headers 已经过期，走的就是这条。

这条路曾经点不进去

后端一直支持（_api_probe 的拒绝条件是「没有效行且没勾 全量」），但前端「开始探测」按钮的启用条件只看「解析出有效行」—— 于是留空输入框时按钮是灰的，纯体检这个需求事实上不存在。

现在按钮认 hasRows || full，两种情形都能点，且确认弹窗按 「有没有同时加新站」分开写 —— 影响面不同，用同一句话会让纯体检看起来 也在往里加东西。

先去重：条目数不等于要探几次

config.yaml 的条目是「(凭据, 段)」的组合。很多中转站用同一把 Key 提供多种协议，于是同一个 url+key 被写进 2-4 个段。

实测那份生产配置：121 个 YAML 条目 → 177 个组合 → 79 个凭据

9 个凭据跨全四段、11 个跨三段、49 个跨两段。而探测的语义本来就是 「拿一个凭据把四段各打一遍」—— 按条目喂它等于同一个凭据重复探 2-4 次， 白打 98 次全流程。

去重键取 (host, api_key) 而不是 (base_url, api_key)： 同一个站在不同段的 base-url 形态不同（codex/compat 带 /v1， 另两段不带），用后者会把同一个凭据判成两个。

探到原上游在别的段也能用：加进去，并算进整体

上面那个数字还有另一面：79 × 4 = 316 个 (凭据, 段) 组合里， 实占 177，空着 139 个。而全量重探对每个凭据的四段都发探测，所以中转站 「先只卖 claude、后来加开 codex」这类新能力它是能发现的。

上一版把这件事整个挡掉了，而界面按「没有闸」渲染

2026-09-02 那次事故（条目从 121 变 246）的修法是 owned_sections + only_owned：「原来没配这一段就 跳过」。它挡住了事故，也挡住了这个需求 —— 而那 139 个空位里，探测跑通的正是 最该新增的条目。

更糟的是那道闸只存在于 rebuild_config_full 内部： build_plan 给那些段的 writable 与 recommended 都是 True，界面显示「建议写入」并默认勾上，勾了写 不进，只在写回后的 warnings 里留一句话。代码里有闸、界面按没闸渲染， 是这一类缺陷的通用形态。

现在判据换成「这一段这次有没有依据」，而不是「原来配过没有」：

模型清单来自落盘 界面
probed 实测跑通推理作为新条目写入 「新增段」徽标 + 建议写入
manual 你手填的清单写入 「手填」徽标
catalog 站方目录声称有写入，默认不勾 「目录」徽标 + 需人工确认
seed 工具兜底猜的不写 「不写入」，并说明手填真实清单即可放行

最后一档是硬闸，它挡的正是 121 变 246 那次事故：那些新增段的清单只是猜测， 凭据在那一段没有任何依据可用，写进去只让 CPA 每次轮到它吃一次失败，耗掉 request-retry × max-retry-credentials 的预算。

catalog 与 seed 的差别不是「可信度高一档」这么模糊： 目录里的名字是这个站自己报的，种子清单是本工具写死的猜测，与这个站没有 任何关系。

放行判定（mark_new_sections）必须跑在批量定档之前：被拦下的 段不落盘，让它参与定档会白占一个档位（taken 被污染，各站被挤得更 低），影响面也会把不存在的条目算进遮挡关系。而模型清单的用户覆盖要跑在它之 前 —— 那道闸按 model_source 判，手填的清单必须先落进方案， 否则「手填了真实模型」仍会被当成猜测拦下。三步的顺序是：覆盖模型 → 放行判定 → 批量定档 → 覆盖 priority。

定档先按证据分档，再按分数

四段全灭的站与实测通过的站排在同一档，字母序决定谁上去

score_verdict 对 usable=False 一律返回 0，而站级排序 原来是「组内最高分降序，同分按主机名」—— 于是「探测全灭」与「探测通过但扣满 分」落在同一档，之后主机名的字母序就成了唯一判据。

2026-09-03 那次真实探测：hotel.example 四段全灭（WAF ×12）却在 claude 段拿到该段第 2 名、gemini 段第 2 名，纯粹因为 ai. 开头。 claude-sonnet-5 与 gemini-3.1-pro 的顶层承载因此换到 一个刚被判死的站上 —— 层级隔离下顶层站不可用时那一层整个白撞一轮 （scheduler.go:402 只取最高那一桶）。

判据换成 model_source（这一段这次有没有依据）而不是 score（探测质量）：probed 0 档、 manual / catalog 1 档、seed 2 档。 同档内仍按分数、再按主机名 —— 稳定性不能丢，否则同一批输入两次运行给出不同 档位，diff 无法复核。

修复后 claude 段 8 个 probed 站占 493-500，5 个 seed 站掉到 170-175；两个热门模型的顶层回到实测通过的站上。

组内证据不一致时点出来：同站多 Key 共用一档是对的（同一个上游、能力 相同），但「这一档由谁的实测撑起来」得说清。实测 golf.example 的 claude 段 7 把 Key 里 6 把实测通过、1 把余额 耗尽走了种子猜测 —— 那一把因此拿到与实测同档的 494，并把 3 个它自己都没验过的 模型顶上了顶层。档位不改（改了就违反「同站同档」），但 priority_reason 里会写「本 Key 的清单来自工具猜测，同档是同站 其他 Key 的实测撑起来的」，那句话原样落进 config.yaml 的行尾注释。

重探既有站不改它的档位

同一个上游地址、只是 token 不同的几条，priority 不一致

2026-09-04 现场截图：kilo.example 的 claude 段 5 条里 3 条 372、 2 条 164；tango.example 14 条里 9 条 371、5 条 167。这与上面刚说 的「同站同档」直接矛盾 —— 定档函数本身是对的，问题出在它处理的对象 与落盘那一步。

两个独立成因，各自都足以造成拆档：

① assign_priorities 把重探的既有站也当新站：算 cap、按分数排、 逐站取 min(cap, 上一站 - 1)。而 taken（不许相撞的 档位集合）是从 cfg 读的，里面塞着这些站自己的旧档 —— 于是每个站都躲开自己原来的值往下掉。拿生产配置实测：claude 段 12 个站从 1000/995/990/985/700/650/630/600/400/350/300/50 变成 500..489 一片连号。

② 留守条目（用户没勾 / 判不可写 / 探测异常）由 _orphan_entry_lines 原样搬回来 —— 原样包含 priority，于是它们留在旧档，与被重探那几把的新值并存。

语义依据：priority 决定「哪一层先被尝试」，层级隔离下只取 最高可用桶（availableAuthsFromPriorityBuckets， selector.go:527-553；priorityOrder 降序， scheduler.go:1229-1231）。既有站的档位是先前一轮定下的站间 次序，重探一次不构成改它的依据 —— 重探验证的是「这把 Key 还能不能用」， 不是「这个站该排第几」。

existing_host_tiers(band) 先算出每个站在本段已占的档（取最高那一档 作锚，低档的实际不参与首选），按 host 命中的直接沿用， priority_reason 写「沿用该站在本段的原档 N」；只有真正的新站才进 空档分配流程。唯一的例外由 _hijacks_at 兜：沿用原档会抢走别人 的顶层时（成因只有一个 —— 本次给这个站注册了它原来没有的模型，而那个模型的 现有顶层比这个站的档位低）才按新站流程重新定档，并给一条警告。

落盘那一半在 _orphan_entry_lines 里修：留守条目的 priority: 行对齐到同站的新值，其余字段与注释逐字保留，行尾注释换成 「对齐同站档位 · 本次未重探此 Key」。值本来就相同时不改也不报，不制造无意义的 diff。

为什么两处都要修，而不是只修一处

只修定档那一处不够：用户手工改 priority 是在定档之后 应用的，那时只有留守条目的对齐兜得住。只修落盘那一处也不够：全勾时没有任何 留守条目，而站间次序仍会被整批推平。

最终不变式落在真实配置的演练里（rehearse_real_rebuild 第⑤组）： 落盘后每个 (站, 段) 只能有一个 priority， 全勾与「隔一把勾一把」两种情形都比。原文件里本来就拆开的站按最高档对齐并 报出来 —— 那是本次之前留下的状态，但会让「同站同档」无从判断。

为什么 websockets 必须实测而不能照抄别的条目

后果不对称：

· websockets: true 而站方不支持 → CPA 走 WS 通道且 不回落 HTTP（CodexAutoExecutor 只按下游形态与该开关 分流，codex_websockets_executor.go:71-77）—— 那个凭据的 WS 请求全废

· websockets: false 而站方支持 → 只是用不上 WS，无害

所以默认必须是「不开」，只有实测 101 才开。

握手与 CPA 的 dialCodexWebsocket （codex_websockets_connection.go:30）同构：URL 是 {base}/responses 的 http→ws 换 scheme（与 buildCodexResponsesWebsocketURL 逐行对齐，只换 scheme）； 头带 Authorization: Bearer 与 CPA 无条件保证的 OpenAI-Beta: responses_websockets=2026-02-06 （codex_websockets_request.go:102-105）—— 少这个头站方可能回 400，那测出来的是「没带门票的握手不通」而不是「不支持 WS」；再叠加该段 已学到的最小必需头。

用标准库手搓握手，不引第三方（本项目零依赖）：只需要状态行那一次，帧收发 不需要。校验 Sec-WebSocket-Accept —— 光看 101 会把 「反代吞了 Upgrade、自己回个 101」当成支持，accept 值是 key + GUID 的 SHA-1 base64（RFC 6455 §4.2.2），算不对就不是 真正的 WS 端点。

need_proxy 的段不探：CPA 的 WS 拨号走 newProxyAwareWebsocketDialer 会用条目的 proxy-url， 而这里直连 —— 直连拿到的 403 说明不了走代理时的行为，那是「拿一个不成立的 实验下结论」。记 None（未探测）而不是 False。

注释保全：两种写法，两种做法

上一章的行级插入保注释靠的是不碰它们。全量重写做不到这一点—— 所有条目都要重新渲染，注释必须主动挂回去。

行级插入（增量）
  • 只在段尾追加
  • 既有的每一行原地不动
  • 注释自然保住
全量重写（重探）
  • 条目全部重新渲染
  • 按 (段, name/base-url) 给注释建索引
  • 渲染条目时按索引挂回去

全局配置（host/port/tls/remote-management 那些）按「第一个 *-api-key 段之前」整段原样保留，不参与重建。

文件里的排序与 CPA 的优先级方向一致（此前这里写反了）

重建后的条目按 priority 降序排列，而 CPA 的语义是 数值大的先被尝试：priorityOrder 按降序排 （scheduler.go:1197-1199），取候选时取数值最大的那一层 （scheduler.go:402 与 selector.go:541-543 都是 priority > bestPriority）。所以文件里排在前面的正是先被 尝试的。

缺这个字段时 authPriority 返回 0 （selector.go:365-372）—— 那是最低优先而不是最高， 所以「不写 priority」等于排在所有显式写了正数的条目之后。

此前本文与 README、DESIGN 都写成「数值小的优先，scheduler.go:1085 升序排序」。那个行号上根本不是排序代码，结论也与源码相反 —— 立论依据不成立 的判断，改的时候要连依据一起换掉。

写回链一步没少

全量重写用的是同一条写回链：基线比对（被改过就 409）→ YAML 校验 → 写前备份 → 就地 O_TRUNC 覆写 → PUT 触发重载 → 端到端验证。

与 CPA-Manager-Plus 的并发写（2026-09-04 读源码后订正）

CPAMP 的配置页确实走 PUT /config.yaml （services/api/configFile.ts:19），提交的是整份文件内容 —— 但它不会丢注释：编辑走 yaml 库的 parseDocument + setIn 再 toString() （hooks/useVisualConfig.ts:920 的 applyVisualChangesToYaml），那是保留注释与格式的编辑方式， 不是「解析成对象再重新序列化」。

它自己也做基线比对：提交前重新拉一次 fetchConfigYaml() （ConfigPage.tsx:893-912），与打开 diff 时的快照不一致就 放弃保存，把改动重新应用到最新内容上让人再确认一次。

但那条安全通道与四段无关。useVisualConfig.ts 的 setIn/deleteIn 路径一个 provider 段都不碰 （只动 auth.providers.config-api-key 一处）—— 配置页管的是 全局配置。真正会改四段的是下面这条。

★ CPAMP 的 provider 编辑会整份回滚本工具的改动（2026-09-05 实测订正）

上一版这里写「两边都有基线比对，都挡不住同一秒的并发」—— 那个结论方向是错的。实际是 CPAMP 覆盖本工具，而窗口宽得多。

CPAMP 改一个 provider 走分段 API（PUT /claude-api-key 等）， 落到 CPA 的 PutClaudeKeys （internal/api/handlers/management/config_lists.go:567-598）：

h.cfg.ClaudeKey = arr     ← 只换这一段
h.persistLocked(c)        ← 但把整个 h.cfg 重新序列化落盘

而 h.cfg 只由 fsnotify 那一路刷新，前面有 150ms 与 1s 两道 debounce（internal/watcher/watcher.go:87 与 :89）。 这条路上没有文件级基线比对 —— GET /config 读的是 h.cfg（config_basic.go:31），不是磁盘； 30 秒前端缓存读的也是它。

三步实测（真实 config.yaml、CPA 自己的 LoadConfig + SaveConfigPreserveComments、全在临时副本上）：

时刻发生什么 磁盘状态
T0CPA 加载配置 claude=65、gemini[0].priority=280
T1本工具就地覆写：加一个 claude 条目、把 gemini[0] 改成 999 claude=66、priority=999
T2CPAMP 用陈旧的 h.cfg 发一次 PUT /codex-api-key（body 原封不动） claude 回到 65、priority 回到 280

新条目的 api-key、prefix，连同它那一行人工注释 一起消失。HTTP 200、validate 通过、零警告。

所以窗口不是「同一秒」，而是「从 CPA 上一次 config 重载到现在」。 全量重探要跑几分钟，这几分钟里 CPAMP 任何一次 provider 编辑 （改 priority、开关站点、改 headers）都会把已落盘的改动整份回滚。

反方向不成立：本工具的 _api_apply 在 _apply_lock 内做原文比对，CPAMP 写过就回 409 要求重新生成。

结论：全量重探期间不要在 CPAMP 里碰任何 provider。 写回完成后等 2 秒（两道 debounce 之和）再去 CPAMP 操作。

Accounts 页的批量操作碰不到 config.yaml 的条目

上一版这里写「凭据字段的批量改动（含 websockets）走管理 API 的 patchFields，逐字段 PATCH，不整份重写」—— 事实层面对， 但把它算成另一条写 config.yaml 的路，那是错的。

config.yaml 里的 api-key 条目根本不出现在 GET /auth-files 里：buildAuthFileEntryLocked 要求 attrs["path"] 非空，而 config 合成器从不设它 （只有文件来源的 file.go 设）。所以 Accounts 页的批量 websockets / priority / weight 对 config.yaml 条目完全不可达。

唯一的例外是 PatchAuthFileStatus → toggleConfigAPIKeyExcludedAll（会写 excluded-models: "*"），但它也因为列不出来而进不去。

这条待现场确认一次：curl -s .../v0/management/auth-files | jq '[.files[].source] | group_by(.)|map({(.[0]):length})' —— 如果线上的 filestore 给 config auth 回填了 attrs["path"]，那就会多出第三条写 config.yaml 的路。

CPAMP 落盘的保真度（同一轮实测）

注释不丢：1758 行整行注释、152 处行尾注释、10 个空行、全部键计数 零变化，0 行孤儿注释。此前担心的「用了 CPAMP 就丢掉 4676 行注释」 不成立。

唯一的外观改动是行尾注释的列对齐被压掉：144 行 priority: 280        # … 变成 priority: 280 # …。本工具下一次做原文比对时， 这 144 行会算成「文件被改过」—— 那不是数据损坏，但会触发一次 409 让人重新生成方案。

条目级与模型级的未知键会被剪掉（pruneMissingMapKeys， config_yaml.go:721-750）：比当前 CPA 版本更新的字段， 经任何一次 CPAMP 分段保存就没了。顶层未知键保留。 这与本工具 extract_carry_lines 的原文行搬运恰好互补 —— 本工具保得住，CPAMP 保不住。

全量重写为什么改成「只替换四段」

第一版的做法是「取第一个段之前的行当全局配置，再从方案生成四段拼上」。 那个方向错了，代价是三个数据销毁缺陷 —— 而它们的共同特征最值得记住： 产出的 YAML 完全合法，validate() 报成功，警告为空。

三个缺陷，实测复现

· 排在第一个段之后的全局键全部消失。api-keys（客户端 认证凭据，丢了所有客户端立刻断连）、remote-management（含管理 密钥）、quota-exceeded 一起丢。

· 某段没有可写方案时整段消失，哪怕原文件里有条目。触发条件低到 「这一段的站这次全部判重复」。

· 段头正则写的是 openai-api-key —— 那个键不存在。真正的 openai-compatibility 匹配不到，被当全局配置复制一遍后再生成 一次，产出两个同名顶层键。yaml.safe_load 静默取后者， 原 provider 消失。

现在的做法：拿原文件逐行走，只在四段的 span 内替换内容，其余原样输出。 没有可写方案的段保留原条目并给警告；原文件没有的段在末尾新建 —— 两件都要，只做前者会让「原本没 codex 段但这次探到 codex 可用」的方案静默 无处安放。

weight: 0 必须搬回去

丢了它 = 手工封禁的站全部复活

weight: 0 是「把这个站逐出调度池」的唯一表达方式，而 CPA 缺这个字段时默认 1。第一版的 render_entry 完全不写它。

在那份真实 config.yaml 里查到 6 个 weight: 0 条目 —— 不修的话全量重探会让那 6 个你手工封掉的站一起回到轮询池，而且没有任何提示。

讽刺的是工具本来就理解这个语义：定档算法把 weight: 0 当作 「挡住它零代价」的强信号读。读得懂，写的时候丢了。

它的查表键必须含段（2026-09-03 对账发现，与 proxy-url 同一个 成因）：原来按 (host, api_key) 索引、跨段共用一个值。实测 facai 的 3 把 Key 在 codex 与 claude 段是 weight: 0（那两条路径静默换模， 已封），在 compat 段故意没写（那条路径可用）；xray 的 3 把同样只封 claude 段。按两元组搬会把 0 灌进那些没封的段 —— 6 个 (凭据, 段) 组合被无声逐出调度池，而 YAML 合法、写后验证也发现不了。

还有一处只在 compat 段出现：它的 weight 挂在 api-key-entries 的每一项上，而 render_entry 的 compat 分支从来不写这个字段 —— 那把 weight: 0 一直只靠 carry 原文行 侥幸活着。组内孤儿 Key 与新增的 Key 都没有原文行可搬，于是照样复活。

compat 段：组内的 Key 会整把消失

前三段有孤儿兜底，compat 段没有

compat 段的结构是「一个 provider 条目 = 一个站，多把 Key 挂在它的 api-key-entries 下」。_orphan_provider_lines 只保留 「整个 provider 都没被碰到」的条目 —— 被碰到的 provider 整条重写， 组内少一把 Key 就少一把。前三段有 _orphan_entry_lines 兜这件事， 这一段没有。

而「没进方案」有三种完全无害的成因：用户只勾了一部分、那个段判不可写、探测抛 异常（BatchProber 会把那个凭据整个从 results 里去掉）。实测生产 配置 gorou.example 15 把、tango.example 14 把 —— 一把出问题就丢一把。

同一处还藏着第二个缺陷：per-key 的 proxy-url 被统一成组内 head 那把的值。实测 kilo.example 5 把、hotel.example 3 把带 per-key 代理，组内不一致时全组按 head 写 —— 多一跳不会失败，所以 validate 与写后验证都发现不了。

修法是新增 compat_key_blocks()：把每把 Key 自己的续行按 (host, api-key) 索引出来，渲染时按键合并 —— 原文有 proxy-url 就尊重原文（那是操作员的显式配置），原文没有才补方案里的。 不是二选一：只搬不补会吞掉本次实测结论（某把 Key 原来只有 weight: 0、这次探测判定它需要代理，那条 proxy-url 就再也写不进去）。

连带修掉一处分组键的问题：compat 组原来按 (host, base_url) 归并， 而同一个站的 base-url 可能有两种拼写（尾斜杠、/v1、scheme 大小写）。 那会分成两组、渲染出两个同 host 的 provider，而 key_blocks 与 _orphan_provider_lines 都只按 host 索引 —— 同一批孤儿 Key 被灌进 两个条目，同一把 Key 在池子里占两个位。改成只按 host 归并，并在拼写不一致时 给出警告说明采用了哪一种。

那 116 条 request-scoped-errors 的代价，配置注释自己记着

「实测 65 分钟内两个 $-0.11 的 Key 产生 52 次 403 insufficient_user_quota， 且把 request-retry(1) × max-retry-credentials(2) 的尝试预算吃光，导致 59 个请求直接向客户端返回 500，而健康凭证根本没轮到。」

实现踩的三个坑，都靠拿真实配置对账才暴露

· 嵌套 dash 误触发条目边界 —— request-scoped-errors 底下的 - status: 403 也是 dash 行。按「有没有 dash」判断会在每个嵌套项上清空缓冲，106 个待搬条目 只搬出 39 个。改成按该段条目级缩进判断。

· 行尾注释挡住 base-url 解析 —— 配置里有 base-url: "https://x.com" # 注意不带 /v1，值带注释时 host_of 解析不出主机名，28 个条目索引不到。新增 _scalar_value() 剥行尾注释，且只在引号闭合之后才认 # —— 值本身可以含井号。

· 同 host 不同 Key 互相染色 —— 某站三个 Key 里只有一个有 fingerprint-profile，按 host 索引会让另两个也拿到（1 → 3）。 改成 host\x00api-key 精确键，且空 carry 也要记 —— 那是「这个凭据确实没有额外字段」的有效信号，缺了它就会退到兜底键。

写后验证抢在 reloadClients 之前

真正让新上游可被选中的是 reloadClients()，它挂在 fsnotify 那一路，前面有 150ms debounce（watcher.go:87）。而 PUT /config.yaml 只更新管理 handler 的 h.cfg （config_basic.go:162-168）。

所以 PUT 返回 200 时凭据池还没重建 —— 立刻打业务端点会打在旧池子上， 刚写进去的站被报成「验证失败」，而它其实是好的。验证前等 1.2 秒 （debounce + LoadConfig 与重建的余量）。误报一个可用站的代价是用户把它删掉， 而这一步只花固定 1.2 秒。

一批站不能都拿同一个值

写回落盘后 claude 段 74 个条目全是 175、gemini 段 76 个全是 225。根因在 suggest_priority 一次只回答「这一个站该放哪」， 而它问的是「当前 config.yaml 有哪些空档」—— 整批算完之前那份文件不会变， 于是 79 个凭据串行调用它、拿到同一个答案。priority 的唯一作用就是 区分先后，全同值等于这个字段没写。

同站同值，站间不同 —— 这是 CPA 的调度语义，不是审美选择

原 config.yaml 三段无一例外：kilo.example 5 个 Key 全 1000、 tango.example 14 个全 990、gorou.example 15 个全 985。

priority 决定哪一层先被尝试，同层内部按 weight 轮询（selector.go:539-549 只取最高那一桶）。同站多 Key 指向同一个 上游、能力相同，本该在同一层。给它们不同值会让第 2 把 Key 只在第 1 把不可用时 才被碰 —— 把「多 Key 轮询」变成「主备切换」，白费配额。

第一版修法绕开了安全边界

第一版直接从空档由高到低铺值：站按探测质量排序，一个站一个值。 「各站分开」这件事做到了，但它没走 suggest_priority —— 于是第 05 章那三条硬约束（不动现有值、不劫持顶层、试用期进最低可插档） 一条都不生效。拿生产 config.yaml 实测（14 站 × 3 Key）：

修后四段全部 0 劫持、最高档挡 0-1 个在用站、站内多值 0、站间重复 0。

空档太窄时整批下移

claude 段高位档位谱极密（1000/995/990/985 相邻只差 5），14 个站挤进去 成了 999/998/997… 正确但没法手工微调 —— 改一个值就撞邻居。

所以站数超过该空档容量两倍时，往下找更宽的空档整批下移。代价约束不松： 只接受「挡住的在用站数不多于原档」的空档，找不到就保持原样。生产 config.yaml 上符合这条的：claude 500(挡0) → gap(50,300) 容 249 个仍挡 0；codex 425(挡1) → gap(10,300) 容 289 个仍挡 1； compat 的 45 已在最低空档，没有更宽的可换。

代价是新站整体排得更低。这是明确的取舍：宁可低一点，也要留出手工调整的空间。

四类提示必须回到界面

/api/plan 一直返回 warnings，而前端从来不读它。 定档退化不影响单个条目能不能用，它改变的是哪个站先被尝试 —— 悄悄发生等于这一轮没修。现在显示在方案页顶部：

  • 整批下移 —— 排不进算法给的空档，已下移到哪一段区间
  • 越过现有档位 —— 哪几个站与那批现有站的先后关系变了
  • 压到最低值 1 —— 再往下无可用整数，这些站会同层轮询
  • 手工改出的同层 —— 用户覆盖在 assign_priorities 之后应用， 把 A 站改成 B 站的值两站就同层了。同层按 weight 轮询是合法配置， 但它取消的正是「不同网站不同优先级」，所以 priority_collisions 在覆盖之后再查一遍

模型清单：段级规则 + 同系列取最新 + 在线名录

现在单一实现在 cpa_probe/model_catalog.py，前端有一份逐条等价的 拷贝（浏览器里跑不了 Python）。tests/test_web.py 拿同一批 36 个模型名 喂两边、逐段比对放行集合 —— 单边改规则会被立刻抓到。

第一版按系列分组，系列是「把版本号换成 *」得到的。 现场截图里 codex 段仍勾着 gpt-4o 与 gpt-5.5：

每一条单独看都「按规则正确工作」—— 系列分组是对的、版本比较是对的。 错在分组的粒度：-luna / -terra 是同一代的 三个变体，不该成为三个独立系列。

现在按产品线分组：剥掉版本与变体后缀（-sol / -luna / -terra / -high / -low / -preview / -nano / -32k / -codex …） 之后剩下的名字就是线名。五个模型全在 gpt 线上，最高世代 (5,6) → 只留 luna 与 terra。

世代只比版本号前两位：claude-haiku-4-5-20251001 解析出 (4,5,20251001)，逐位比较时那个日期戳会让它比 claude-haiku-4-5 (4,5) 更新 —— 而它们其实是同一款。截断到 (4,5) 后两者相等、都保留， 让 CPA 自己去匹配。缺位补 0，所以 claude-opus-5 (5,0) 会被 claude-opus-5-1 (5,1) 挤掉，与语义一致。

整条线都认不出版本时全留（gpt-oss:120b / gpt-oss:20b）—— 无从比较不淘汰，宁可多留一个也不因解析不出版本号而丢掉可用模型。

同一个形态，第三次：o 系列

codex 段同时勾着 o1 与 o3

2026-09-04 现场截图：o1 / o1-pro / o3 / o3-mini / o3-pro / o4-mini / o4-mini-high 七个全勾。o3 是 o1 的后继， 两代一起注册等于让 CPA 的轮询把请求分给旧款。

与 gpt-4o 那次是同一个形态，只是换了一族：版本正则要求 数字前不紧贴字母（(?<![A-Za-z0-9.])），而这一族的数字紧贴 开头的 o —— 于是七个名字全部解析成「无版本」，被上面那条 「整条线都认不出版本就全留」的兜底一起收下。

加一条 _O_SERIES_RE（^o\d+），产品线统一叫 o：七个名字变成 o / o-pro 两条线各取 最高世代 → o3-pro / o4-mini / o4-mini-high。锚在开头且紧跟数字，omni-3 / oss-20b / openai/... 不受影响。

这一改带出一处连带缺陷

catalog_is_stale（判「站方目录整体落后」）原来比两侧的全局 最高世代。给 o 系列补上版本解析后立刻出错：o3-mini 的世代是 (3,0)，而 codex 段的市面最新是 gpt-5.6-sol 的 (5,6) —— 两个数字来自互不相干的编号体系，o3 的 3 不代表它比 gpt-5.6 老一代（两者同期）。按全局比会把「目录里只有 o 系列」 的站误判成落后，从而一个模型都不预勾。

改成逐产品线比：只对两侧都出现的线比较最高世代，全部落后才算落后； 目录里的线在市面清单里没有对应时无从比较，不判落后 —— 与「整组认不出版本 就全留」同一条原则。/api/context 因此多回一个 market_top_gen_lines，前端用它而不再用全局那个数：两边必须同一套 数据，否则界面预勾与落盘清单再次分叉。

无目录时后端填的模型，前端一个都没显示

警告里列着 6 个模型名，那一格却是空白

现场截图：某站 gemini 段「可信模型」完全空白，只有一个提示手填的输入框。 而同一行下方的橙色警告写着「模型清单取自『当前市面最新』（CPA 权威名录 6 个 + 本地 config.yaml 8 个）：gemini-3.1-pro, gemini-3.1-pro-high, …」。

目录为空时前端走 cat.length ? … : … 的 else 分支，只渲染一个 空的手填框 —— 它从 S.forced 取值，而那里此刻是空的。方案里的 sp.models 从来没被显示，也没写进 S.forced。

而提交时读的正是 S.forced —— 所以那个段勾上也写不进任何模型。 用户问「是不是代表写回后这个上游站一个模型都没有」，判断是对的。

修法：else 分支留一个空容器，refreshPlan 拿后端方案的 sp.models 填成勾选框、默认全勾。全选 / 反选 / 清空按钮跟着出现。 容器已填过就不再重填 —— 否则每次 refreshPlan 都会把用户的取消 勾选覆盖掉。

回写 S.forced 只在清单有依据时做（2026-09-03 补）： forced 非空会让后端走 manual 分支，于是 seed 猜测 被洗成「手填」—— 徽标不再提示这批名字没有依据，而跨段新增那道闸按 model_source 判、manual 放行，猜测清单因此能凭空 新增条目，正是 121 条目变 246 那条老路。不回写也不会丢：后端本来就写它自己 算出的 sp.models，界面显示的是同一份。用户真的动了勾选框时 change 事件会写 S.forced —— 那时记成手填是对的，操作员显式做了 决定。

可用行的模型格：只读文本 → 勾选框 + 手填 + 目录补充

「可用 + 实测」的行反而最没法改

可用行的模型格原来只渲染 v.models.join(', ') 纯文本， 三处后果同时存在：

① v.models 为空时显示「无可信模型」，而后端方案里 sp.models 已经有 6 个。_accept() 在静默换模或 「200 包错误体」时拒收模型，段仍算可用（端点确实响应、凭证有效），清单一个 都没进。判死行有 .cats.fallback 容器接住这种情形，可用行连容器 都没有 —— 于是 refreshPlan 无处可填。

② 可用行完全没有手填入口。操作员知道这个站还卖别的模型，也只能去改 config.yaml。

③ 探测收够 max_models（默认 4）个就停，站方目录里其余名字在这 一格看不见 —— 而那些名字往往正是要写进去的。

现在可用行与判死行用同一套 DOM 约定（.cats / .cm / .fm / .mtools），所以事件绑定与 fallback 填充无需 分叉。实测清单打勾、目录里探测没验到的名字列出但默认不勾（实测过的才有 依据，目录只是站方声称），并标一个「目录」小字。

连带修掉一处不对称：.cm（勾选框）的处理器一直会合并手填框里目录 外的名字，而 .fm（手填框）的处理器只取自己的值就整份覆盖 S.forced —— 「勾了目录里 3 个再手填 1 个」的结果是只剩那 1 个， 而 3 个勾选框在界面上还勾着。又是一处「界面勾着、实际没接管」。

手填无条件优先，不看探测是否通过

判据写成 forced_models and not v.usable 堵死两条路

① usable=True 但 v.models 为空：手填的清单落不 进来，反而掉进 seed 分支 —— 界面上「手填」变成「猜测」。

② usable=True 且清单非空：操作员想把探到的 4 个换成自己知道的 8 个，probed 直接盖掉手填，一条警告都没有。

手填是操作员的显式意图，探测判定是工具的推测。推测盖掉显式意图在任何处境下 都是错的 —— 与 force 参数的设计意图一致（它只绕过 usable 判定， 去重 / 定档 / 影响面一道不少）。

改成 if forced_models: 之后要连带改两处措辞，否则说反了就是误导： 覆盖实测清单时说「探测判『可用』（实测到 X），但已按你手填的清单写入」，判死段 照旧说「探测未通过」；手填全部不合规时的兜底说法按实际落到哪儿写 —— 可用段落回 probed（本次实测到的清单），判死段才落到目录或市面 最新，原来写死成「市面最新清单」在前一种情形下是假话。

三层数据源：为什么不能只写死一份清单

层来源它独有的东西
1CPA 权威名录（远程） CPA 实际认识的模型集合。与 CPA 自己的 model_updater.go 同源（每 3 小时拉），所以会自动跟进新版本。 缓存成功 6 小时 / 失败 10 分钟
2本地 config.yaml 已有的模型名 站方特供型号。实测 gemini-3.1-pro-high、 -pro-preview-search、-pro-preview-customtools、 gpt-5.6 四个都不在 CPA 名录里，但就在生产配置里跑着
3内置兜底 前两层都拿不到时（国内 VPS 直连 GitHub 不通是常态）

为什么不能只有第 3 层：写死的清单会过期，而过期的表现是「填进 config.yaml 的模型 CPA 每次轮到都失败」—— 与缺模型一样坏，却更难发现（界面上看着有值）。

排序与轮转：去重之后还有一步

newest_per_series 只做「同系列去旧」，不同系列之间它无从取舍。 取前 N 个时若按输入顺序，拿到的是「CPA 名录 JSON 里排得靠前」的那些 —— 与「哪个模型更该用」无关。实测 claude 段不排序时前三名是 haiku / sonnet / opus，正好倒过来。

所以先 rank_models（主力款 → 变体 → 降级档），再按产品线轮转。 不轮转时 claude 段前四名是 opus-5 / opus-5-thinking / opus-4-8-m-aws / fable-5-1 —— 四个里三个是 opus 的写法， 把 sonnet 挤出去了。

compat 段按族轮转：它的价值正是「一个条目转多族」， 前 N 全是 claude 等于浪费掉这个段。

手填走更宽的一套判据（2026-09-03 修正）。上面那四条管的是「工具 自己要不要挑这个模型」；操作员手填的走 section_protocol_ok， 只挡协议层不可能成立的。两者唯一的差别是四族之外 （grok / glm / deepseek …）： compat 段放行、前三段照旧拒。

按族拒掉手填，会让操作员没法写回已知可用的模型

compat 段走 /chat/completions （openai_compat_executor.go:107），CPA 侧对模型名零校验 （buildOpenAICompatibilityConfigModels 照单注册， service_models.go:713-739）—— 能不能用只取决于上游认不认。

而生产 config.yaml 里 romeo 的 compat 段唯一通过端到端 验证的模型就是 grok-4.6（注释原文：「整个 vip 分组当前只有 grok-4.6 有渠道，已通过端到端验证的只有它」），facai 段还有 grok-4.6 + glm-5.2。

按族拒掉手填，那一段会从「有一个确认可用的模型」变成「只剩两个确认 503 的 gpt-5.6-*」，而操作员没有任何办法纠正。「本工具不主动推荐四族 之外」是选型偏好，把它升级成「操作员显式指定也不许」就越权了。

放行时给一条警告说清「不在四族清单里、已按你的指定写入、工具没验证过」， 不让它看起来像工具推荐的。丢弃项照旧明确告知 —— 手填是显式意图，悄悄改掉比 拒绝更糟。实测手填 gpt-5.6-sol, gpt-image-2, gpt-oss-20b, gpt-5.5, claude-opus-5 时收下合法的那些，并警告「手填的 N 个模型已丢弃」（图像与 oss 属于非对话 模型，四段都拒）。

前端 protoOk 与后端 section_protocol_ok 由 tests/test_web.py 拿同一批模型名喂两边比对，并写死「两者的差别 只在四族之外、且只在 compat 段放开」这条不变式 —— 单边改判定会被立刻抓到。

手填框旁还有一条即时提示，不用等一次 /api/plan 往返： 协议层不成立的标红并说清原因，四族之外的给一句灰字说明。判据同样是 protoOk 而不是 famOk —— 用后者会把 grok-4.6 标成红的，而它恰恰是该写进去的那一个。

目录里一个四族的都没有时，收站方自己报的

同一个形态在目录路径上也会出现，而且是自动路径：按四族过滤后清单变空， 就落进种子兜底、写工具猜的名字。那时的选择只有两个 ——

选项后果
写工具猜的名字这个站从没报过它们，CPA 路由过去大概率 404，把一个「有老模型可用」的站变成死条目
写站方自己报的名字未验证，但至少是这个站说它有的

后者严格更好，所以退这一步：目录里一个四族的都没有时收下协议层成立的全部名字， model_source 记成 catalog，界面与警告都说清「站方目录 里没有本工具四族清单内的任何模型，上面列的是它自己报的 —— 退这一步是因为另一个 选项更糟」。

目录里有四族的名字时，四族之外的照旧不进清单 —— 选型偏好在有得选时仍然 生效。前三段一律按族拒（协议层就发不出去），只有 compat 段的 /chat/completions 真的不限族。前后端同一条规则， tests/test_web.py 守着。

weight: 0 的含义取决于 routing.strategy

本项目多处把 weight: 0 当「站已被逐出调度池、挡住它零代价」的 强信号读 —— 定档算法据此把新站排到它们之前。核对 CPA 源码后发现 那只在一种策略下成立：

策略读 weight 吗 weight: 0 的效果
weighted-round-robin是 positiveWeightAuths 整个剔除（selector.go:650 → 637-644）
round-robin（默认）否 照常参与轮询（selector.go:589）
fill-first否 照常参与轮询（selector.go:787）
默认策略下把零权重站当死站，会把新站插到在服务的站之前

没配 routing.strategy 的部署走默认 round-robin。此时定档以为 「挡住它没代价」，而那些站其实照常出活 —— 方向正是本项目反复强调的更坏 那个：把活站当死站。

当前部署实测配的是 weighted-round-robin，所以旧行为一直是对的； 但那是配置的巧合，不是代码的保证。这类缺陷换一份 config 就会现形， 而测试里的构造数据恰好也没配 routing —— 两边都「碰巧对」。

weight_zero_excludes(cfg) 按配置判断策略（认三种拼法，大小写与空格 不敏感，与 service_config.go:42-47 一致），build_band 据它决定 要不要把零权重站计入 dead_hosts。界面提示也跟着分岔 —— 非 wrr 时说 「当前策略不读 weight，仍参与轮询」，并说明 CPAMP 面板的「未启用」是按 weight 判的、与实际调度不一致。

规则收紧不许把段变成「勾不上」

新规则上线后自查抓到两处「各自合理、合起来出错」：

① 目录非空但全不合规 = 段勾不上

elif v.catalog: 只判目录非空。一个只报 flash / oss / grok 的站， 过滤后是空列表 → models=[] → writable=False → 那个段连勾选框都点不动。这正是 2026-09-01 修过的「判死段勾不上」 被新规则重新引入。改成「目录为空或过滤后为空」都落到市面最新清单。

② 手填全不合规时，「已丢弃」警告永远不触发

手填的全部不合规 → forced_models 变空 → if forced_models and not v.usable 为假 → 落到 seed 分支 → model_source 是 seed 而非 manual， 而那条警告写在 manual 分支里。用户手填了两个、一个都没进去、界面上一句提示 都没有，工具悄悄换成了自己那份清单 —— 正是这条警告要防的那件事。

警告挪出 manual 分支无条件报，并额外说明「已改用市面最新清单」。

兜底放在 else 里，两条路绕过它

「可用 + 实测 + 无可信模型 + 不可写入」四个标记同时出现

现场截图里某站 compat 段就是这四个。_accept() 在静默换模或 「200 包错误体」时拒收模型，段仍算可用（端点确实响应、凭证有效）， 但清单一个都没进。

而前两版把兜底写在 else: 分支里：

elif v.usable: models = list(v.models) —— 空列表也照抄， 不进兜底；else: … if not models: 兜底。

这是第三次修同一处。前两次都只补了自己当时看到的那条路： 第一次补「目录为空」，第二次补「目录非空但全不合规」，都在 else 里面 —— 对 v.usable=True 那条路无效。

判据必须是清单空不空，不是「走了哪条分支」。兜底移到所有分支之外， 三条入口（单站诊断 / 增量导入 / 全量重探）实测都填 6 个。两种处境的措辞 也分开写 —— usable=True 那种说「端点响应正常、凭证有效，但每次 返回的模型都与请求不一致」，不再和「探测未通过」混同。

整份目录都是老款时，列出但不预勾

某站 codex 段目录只有 gpt-4 / gpt-4-32k / gpt-4o / gpt-4o-mini —— 四个都是世代 (4,0)， 于是「同产品线取最高世代」把四个全留下还默认全勾。规则本身没错 （那条线里 (4,0) 就是最高），但违反「最新是 gpt-5.6 时 gpt-4o 不该默认勾选」。

为什么不换成市面最新清单

那个站的目录里确实没有 5.6 系的名字。写进去 CPA 路由不到，把一个 「有老模型可用」的站变成死条目 —— 比默认勾错更糟。

所以只降级默认勾选：清单照旧列出（确知可用可手工勾）， recommended 为假，界面说明「整份目录都落后于市面最新 （本段最新已到 5.6）」。

判据是世代而非名字 —— 站方特供型号不在市面名录里，按名字比会把它误判成 落后。/api/context 回 market_top_gen，因为结果表在勾选 之前就渲染了，那时还没有 /api/plan 的响应，两边都要能判。

2026-09-04 改成逐产品线比：全局比较在 o 系列上会误判 —— 详见上面「同一个形态，第三次」那一节。现在只对两侧都出现的线比较， 前端读的是新增的 market_top_gen_lines。

限频：站方把阈值写在正文里，工具却没用上

同一个站撞了 46 次，每次都用同样的节奏再打一遍

bulk probe guard: ip 1.2.3.4 requested 4 distinct models in 60s

判定「限频」→ 处置写着「加大探测间隔重试」→ 然后什么都没做。 那句正文里带着确切阈值（4 个模型 / 60 秒），读得出来却没用上，等于让用户 去看日志、猜一个 --gap、再重跑十几分钟。

_note_rate_limit 解析出 N 个模型 / M 秒，取平均间隔 × 1.1（滑动窗口，贴着阈值走仍会偶发命中），对该站生效并整站合用一个 gap 桶 —— 这类 guard 按账号/IP 全局计数，按 (host, section) 分桶会让瞬时 并发变成 4 倍，那正是 46 次全撞的原因（第 07.5 章那条「风险与取舍」注释预判过 这件事，只是当时留给用户手工调）。

只收紧不放松（更松的响应不覆盖已学到的严格值），荒谬窗口钳在 60 秒 —— 见过站方报 3600s，照抄会让整批探测卡死。

为什么换代理不是解法

站方数的是「这个 IP 在 60 秒里问了几个不同模型」。换到代理出口后 同样的节奏立刻又触发一次，只是白烧一次请求并把代理 IP 也搭进去。

_PROXY_POINTLESS 里「限频」那条早就写着「探测节奏问题， 加大 gap 而非换 IP」—— 那张表存在的意义正是让「为什么不试代理」可追溯。

上下文上限：10 个 token 的窗口

这个值会让整个站不可用，而 validate 报成功

实测日志里一个 compat 站三个条目都拿到 max-context-length: 10。 CPA 把它直接当 context_window / max_context_window 报给 客户端（models.go:206-211）—— 客户端按 10 个 token 定压缩点， 那个站每一次请求都立刻超限。

根因：_bisect 的截断判据是 tok < chars * 0.5 就把 tok 当真实容量。上游回 input_tokens: 10（它根本没统计， 或统计的是别的东西）时，10 就成了「实测容量」。

加了下限 _MIN_TRUSTED_CONTEXT = 8000：比任何真实模型的窗口都小一个 数量级（现役最小的也有 200k），不会误伤真实小窗口站；低于它就当「测不出」 并发 context-untrusted 事件说明 —— 缺这个字段 CPA 会回落内置目录值， 比写一个荒谬的数安全得多。

proxy-url 搬运必须按段

existing_proxies 原来按 (host, api_key) 索引，跨段共用一个值。 实测 kilo.example 的 5 把 Key 在 compat 段有 proxy-url: http://mihomo:7890，在 claude 段故意没有 —— 那个站的 claude 路径直连可用，走代理反而多一跳。

按两元组搬运会把 compat 的代理灌进 claude 段，实测 claude 段 proxy-url 从 3 条 涨到 8 条。多一跳不会让请求失败，所以 validate 与写后验证都发现不了 —— 又是一处静默改变行为。键改成 (段, host, api_key) 后前后各段完全一致。

警告与算法必须同口径

「挡住了谁」这条警告原来只报总数，不分活死。演练实测输出：

警告说挡 2 个，算法说无代价 —— 同一件事两个答案

priority 280 会把 2 个现有站挡在其后（hotel.example、mike.example）

而那两个站在 config.yaml 的注释里都记着实测不可用，定档算法数出的在用站 是 0（第 05 章：挡住一个已经不可用的站代价为零）。用户看到的是警告， 于是会去调低一个本来最优的档位。

README 那时已经写着「这条警告会区分被挡的是活站还是死站」—— 文档超前于实现。 这类不一致比缺功能更难发现：读文档以为有，看输出以为对，只有拿真配置跑一遍 才对得上。

现在下层全是死站时改说「排在 N 个现有站之前 —— 它们全部已实测不可用或 weight:0，挡住它们无代价」，并提醒这些站若日后恢复档位不会自动重算 （weight:0 与注释结论都不会自动过期）。活死混合时主句只计活站， 死站另说一句。给的替代值也从「少挡 N 站」改成「少挡 N 个在用站」。

raw 漏传一处，三条途径就给出不同的 priority

build_band 只在拿到 config.yaml 原文时才解析注释里的 「实测不可用」结论，而那直接决定「挡住下层算不算代价」。漏传不报错， 只是把可用新站压到一堆死站后面。

实测差距（满分候选）：claude 段 175 → 500、 gemini 段 225 → 280，另两段不变。

单站诊断此前就漏了这一处 —— 同一个站，诊断页显示 175、全量重探显示 500。 现在网页端两条路径、CLI 与 assign_priorities 全部传。 CLI 还漏过整个批量定档：同一份输入在命令行与网页端落盘出不同的值。

一条方法论

这几批缺陷都是在测试全绿的情况下被专门审计找出来的（第一批 869 项时， 第二批 934 项时、第三批 946 项时）。原因是那些测试的构造数据按我自己的理解写的，跟真实产出 不一样 —— 测试只能证明代码符合我的意图，不能证明我的意图对。

第二批更进一步：拿生产 config.yaml 逐字段对账，把重建前后的 15 个 字段计数与每个条目的每个字段值全部比一遍。这一步立刻暴露了三个坑， 而它们在假上游的构造数据里都不出现 —— 因为构造数据是「我以为配置长这样」， 真实配置是「配置实际长这样」。

新测试一律锁在「实测复现过的破坏」上：全局键要在、无方案段要保留、顶层键 不能重复、weight: 0 与 proxy-url 要搬运、 未知字段要逐字保真、同 host 不同 Key 不能互相染色、cgroup 异常值要降级。

如实说明：验证到哪一步

已验证：假上游套件、单元测试（1196 项，含真实 config.yaml 用例时 1198 项）、端到端演练、以及拿两份生产 config.yaml 做的重建对账 （tests/rehearse_real_rebuild.py，各 52 项全对上：121 条目 / 79 凭据 / 177 个 (凭据, 段) 槽位，逐字段值零差异）。

那份对账值得单独说，因为它抓到的十处缺陷单元测试全绿：headers 整字段消失 （Desktop 版 24/24、fsdownload 版 66/66 条目，含 anthropic-beta 24 条 —— 见下方单独一段）、compat 段组内没进方案 的 Key 会消失（生产配置 gorou.example 15 把、tango.example 14 把）、per-key 的 proxy-url 与 weight 被统一成组内 head 那把的值 （8 把带 per-key 代理）、同一个站两种 base-url 写法会写出两个同名 provider、 prefix 被 dominant_prefix 猜的值覆盖（121/121 条目， ANT/xxx 别名全失效）、compat 的 name 被改成 host （12/13 个 provider 改名，那是 CPA 的 provider 身份，改名作废冷却状态与能力 缓存）、注释索引把模型名当条目键且 base-url 行尾注释没剥（4676 行注释里 118 行彻底丢失）、模型级 max-context-length 8/8 消失 （它在 models: 块内，carry 有意跳过那一块，而方案只带本次实测的 那一个 —— 三方都不管的空档）、重探既有站被当新站重新定档（claude 段 12 个站 从 1000..50 变成 500..489 一片连号）、留守条目的 priority 留在 旧值（同站被拆成两层，「多 Key 并行」退化成「主备切换」）。

headers 那一处更深一层：判据本身漏了它

值确实逐个比过了，但 headers 被列进对账脚本的 INTENT（「本次有意改动，跳过」）豁免名单。于是 52 项全绿， 而 24/24 条目的 headers 全丢没有任何一项能看见。

它是四段条目级字段里唯一「只生成、不搬运」的那一个：在 _RENDERED_KEYS 里所以 carry 不搬（那是给白名单外的 字段用的），而 existing_* 查表以前没有它。方案侧的 headers 只在探测当场判定 need_ua 时才有值 —— 重探时那个站 baseline 就通的话 sp.headers 是空 dict，那一行整个写不出来。

后果是真的改运行行为：条目级 headers 一路到达上游请求 （config.go 的 addConfigHeadersToAttrs → attribute header:<Name> → util/header_helpers.go 的 ApplyCustomHeadersFromAttrs），所以丢掉 anthropic-beta: context-1m-2025-08-07 就是把那个站的 1m 上下文关掉，而 YAML 合法、validate 报成功、写后验证也 发现不了。

INTENT 已从 {priority, models, headers} 收窄到 {priority, models}。

其余几处是逐字段 deep-equal 才抓到的：之前只比字段的出现次数 （text.count("prefix:")），而「121 个条目的 prefix 全被抹掉、 同时注释里多出 121 处提到 prefix」这种情况两边都数得对 —— 计数相等，值全错。 最后两处更进一步：字段值也逐个对上了，缺的是跨条目的不变式 —— 「每个 (站, 段) 只能有一个 priority」， 单看任何一条都合法。合成样本一个都碰不到 —— 13 个 provider、69 把 compat Key、4676 行注释这种形状只有真实文件有。

未验证：没有对这 79 个真实站跑过一次真实探测，也没落盘到生产 —— 对账用的是「把既有条目原样当探测结果」，验的是写回链的守恒性，不是探测本身。 第一次实跑建议看完 diff 再决定是否写回，备份是唯一的回滚手段。

2026-09-05：与 CPA 对齐，以及一批安全加固

每一处都跟了撤销验证

做法：把修复改回旧行为，跑对应套件，确认它真的变红。 只有变红才证明那条断言守住了这个修复。

这一轮撤销验证抓到七次假绿 —— 断言存在、测试通过，但把产品代码改坏 之后它照样通过。共同形态是断言的是一个比要守护的性质更弱的代理指标：

我写的断言它挡不住什么
「查表函数被调用 + 结果被赋值」（AST 层） old = None —— 那一行仍然调了、仍然赋了，只是赋的是空

那样响应就是 SSE，而整条判定链读的是 JSON 正文（resp_model / input_tokens / has_error_envelope / betas.wanted）。改了等于把一种假阳性换成另一种。

所以加了一档 codex-cpa-shape（tier=4，排在 codex-full 之后）：它只回答一个问题 ——「CPA 那样发，这个站收不收」。复用已有的 body_patch 机制（claude 段的 metadata.user_id 就走它）， 不需要新框架。

加完立刻发现一处结论相反的错误提示：config_advice 原来按 段分岔，于是把新档报成「该站要 metadata.user_id，配置层无法表达， 只能人工接管」—— 而正确结论正好相反：那一档的 body_patch 是 CPA 自己会加的东西，通过说明什么都不用做。改成按 body_patch 的 内容分岔。如果不看这条提示，界面会给出与事实相反的建议。

安全加固：唯一不需要登录就能打的那个

nginx 后所有来源 IP 塌成 127.0.0.1，5 个请求锁死全站 30 分钟

服务只在 127.0.0.1:8765 监听、由 nginx 反代，于是 client_address 对每一个访客都是 127.0.0.1。 失败封锁按它索引 → 整张表只有一个桶：

任何人对任意路径连发 5 次带假 Bearer 的请求
  → 之后 30 分钟运维本人也进不来（_authed 在比对密钥【之前】就查封锁）
  → 容器 restart: "no"，不自愈

每 30 分钟重打 5 次即永久封锁，而它宣称的暴破防护对真实攻击者完全无效 （换 IP 与不换等价）。

修法是读 X-Forwarded-For 的最右一跳 —— nginx 用 $proxy_add_x_forwarded_for，链条是 <客户端可伪造>, <nginx 看到的真实对端>。 取最左（常见写法）等于让客户端自己声明 IP，那比不读还糟：攻击者每次 换个伪造 IP 就绕过封锁，而运维的真实 IP 反被封。只在直连对端是回环时才信 这个头。

同一批必须加的是封锁表的容量上限：修好真实 IP 之后这张表的键从 「恒为 127.0.0.1」变成攻击者可控，不加上限就是把一个 DoS 换成另一个。 淘汰顺序也是判据 —— (是否在封锁中, last) 升序，否则攻击者能用 大量新 IP 把自己的封锁记录挤掉。

全量重探的预览把 177 行明文凭据回给了浏览器

server.py 开头自述「完整 key 不进 JSON 响应（一律 masked）」， 而全量重探那条路的 diff 就是重建后的整个文件 —— 不是增量片段。 生产配置里 177 行 api-key: 明文 + 1 行 secret-key， 共 349KB 全部进浏览器 DOM，界面的「复制」按钮还会把它们写进系统剪贴板。

修法是按行脱敏，只动值不动结构：行号、缩进、注释、其余字段全保留， diff 仍然完全可读。落盘走的是服务端内存里的原文，不受影响。

为什么不改成「不给全文」：全量重探的价值就在于「写回前看清整个文件会 变成什么样」，给一段掐头去尾的片段等于把这个功能废掉。

上游返回的模型名会被拼进出网 URL

模型名来自站方的 /models 目录（第三方完全可控），而它被直接拼进 f"{base}/v1beta/models/{model}:generateContent"。 实测通过原来全部闸门的名字：

名字后果
../../../gemini-3.1-pro 逃出 base 路径，打到同主机别的端点
gemini-3.1-pro-x?a=b :generateContent 落进 query，实际请求的是另一个端点； 它回 200 就成了「该模型可用」的伪证

而且不需要拿到 200：方案的 catalog 分支把目录里的名字直接当候选， 这串字面量会进 config.yaml，CPA 用同样的方式拼 URL 再发一次（它也是裸拼）。 本工具是这条链上唯一有机会校验的一环。

关键约束：/ 必须允许

生产配置里 85 个模型名有 Business/gemini-2.5-pro、 anthropic/claude-opus-5 这种分组前缀 —— 那是合法且常见的形态。 实测那 85 个名字用到的非字母数字字符只有 - . / 三个，最长 34 字符。

所以判据是「只许这三个符号 + 禁止路径穿越 + 禁止 query/fragment 起始字符」， 不是简单的「不许有 /」。三层拦：目录解析入口就丢掉 （并在事件流里说出来 —— 静默丢站方数据不好）、两个段级闸门、 以及真正拼 URL 的 build_request 抛异常。

内网去向：这道闸挡的是侦察，不是全部 SSRF

探测目标 URL 与代理地址都来自请求体，而校验只看形态不管去向。两条路都带回显， 其中代理那条更干净 —— probe_proxy 做裸 TCP 连接， 把连通性、异常类名（ConnectionRefused/timeout）、毫秒数经 proxy-precheck 事件回到 /api/job。那是比 HTTP 路径 更好用的端口扫描 oracle。

is_private_target 挡回环、10/8、172.16/12、192.168/16、 169.254/16、IPv6 的 ::1 / fc00::/7 / fe80::/10 / ::ffff: 映射，以及 metadata.google.internal 这类云元数据主机名与 .local / .internal 后缀。

它挡不住什么 —— 必须写清

只看字面量地址，挡不住 DNS rebinding（解析时公网 IP、连接时变私网）。 要防那个得在 client.py 接管地址解析，代价不小。不写清的话， 下一个人会以为这道闸挡住了一切。

云元数据端点本来也打不到 —— 出网路径总在 base 后追加固定后缀 （/v1/models、/v1beta/models、 /v1/messages、/responses、 /chat/completions），拼不出 /latest/meta-data/...；GCP 要的 Metadata-Flavor 头也不会发。所以这是内网侦察而非直接偷云凭据。

问题修法
并发与预算参数无上限 {"max_workers":50000} 就是 5 万站级线程。后果不止本机资源 —— 把大量出网请求打向 121 个第三方站可能触发批量探测防护， 代价落在真实凭据上（封号）。现在集中钳制，输入行数上限 500

当前前端没有可利用的注入点（274 处 esc()、36 处 innerHTML 全核对过），所以这是纵深防御。但这个页面渲染的是 完全由第三方上游控制的正文摘要、模型名、错误消息，而全量重探模式下 DOM 里还有整份配置的预览。

CSP 必须写成一行 —— nginx 不支持反斜杠续行：引号内的反斜杠是转义符， 反斜杠加换行会把一个真实换行塞进 HTTP 头值（非法头，而且是头注入面）。

而且要与前端的实际用法对账：CSP 配太严会让页面白屏，且只在浏览器控制台 警告 —— 服务端一切正常、测试全绿、用户看到一片空白。所以那道测试两个方向都查： 头齐不齐，以及前端有没有 CSP 拦得住的用法（内联 script / onclick / eval / 外部 CDN / 跨域 fetch / WebSocket）。

08

生效链：写完盘不等于生效

这一段全是容器与文件系统的细节，但每一条都决定「改了却没生效」。

备份文件名撞名 = 把唯一的退路弄丢

备份名只到秒、且复制时撞名直接静默覆盖时：同一秒内写两次 （并发写回、脚本连续跑），第二次的备份会把第一次的覆盖掉 —— 留下来的是「第一次写完之后」的状态，真正的原始文件没了。

而就地覆写本身不原子、失败不回滚，备份是唯一的回滚手段。 所以撞名不是「多留一份少留一份」的问题。

并发写回：两个请求都以为自己拿的是最新基线

服务跑在多线程 HTTP 服务器上。「读文件 → 比对基线 → 校验 → 写盘」 这四步之间没有互斥时，两个并发的写回请求会各自比对到同一份 未改动的基线、双双通过，然后依次写盘 —— 后写的覆盖掉前一次的全部改动， 而给前一个客户端回的仍是 200。

顺序执行不会有这个问题（第二次的基线比对会正确地报 409）， 所以顺序跑的测试抓不到它。修法是把那四步整段放进一把锁。

一次外网请求把首屏卡成白屏

输入 token 后很长时间只有页头，正文全空，没有任何提示 —— 看起来像页面坏了。 根因两层叠加，单独看每一层都「合理」：

同步拉 GitHub + 失败不缓存 = 每次都慢

/api/context 同步调画像漂移检测，而远程模式要串行拉两个 GitHub 文件（claude_executor_request.go 与 codex_executor_request.go）。 国内 VPS 直连 raw.githubusercontent 不通，实测每次干等 15 秒； 最坏还能叠上 codex 那个文件 15 秒与 remote_commit 10 秒 = 40 秒。

extract_remote 只在成功时写缓存：

if use_cache and out.claude_betas_unconditional: # 失败时这里为空

所以拉不通的环境根本没有缓存，第二次跟第一次一样慢。remote_commit 连缓存都没有 —— 实测连打三次全走网络。

前端那侧 #gate 与 #app 都 hidden，要等这个响应回来才 #app.hidden = false。页头是静态 HTML 所以立刻可见，中间那段空白就是 没有任何加载提示的白屏。

这类缺陷的形态值得记一笔：它只在特定网络环境下出现。本机能拉通 GitHub， 首次 4.3 秒、之后 0.5 秒，完全不像有问题；只有在拉不通的机器上才暴露成 每次 15 秒。968 项测试没有一项碰到它 —— 它们都不发真实外网请求， 而这恰恰是那个缺陷的触发条件。

修法：把网络请求挪出请求路径

改动效果
_drift_snapshot()：接口只读缓存，缺失或过期时丢给后台线程 /api/context 从不因它阻塞

remote_commit 纳入同一套缓存 少一次每次都走的网络请求

X-CPA-COMMIT 探测也挪进后台线程 那也是网络请求（3 秒），不该抬高接口下限
前端加启动骨架 #bootbox，3 秒后换文案说明原因 首屏不再是白屏，慢也说得出为什么

功能一项没减

三条检测路径（本地源码 / 远程拉取 / config.yaml 的 header-defaults） 与所有输出字段全部保留，只是换成异步刷新。首次打开时漂移那一块显示 「正在核对」，每 3 秒自取一次（最多 10 次，30 秒拿不到就说清并停手）， 算完就地替换。

Variables 在构建日志里是明文；Secrets 会被 Actions 自动打码。 把 token 放进 Variables 等于把它印在每一次构建日志上。

另外：两项必填都要有才会发布。只设用户名、稍后再加 token 是很 自然的操作顺序，而那样会让每次构建都红在 401 上，且看不出是「token 还没配」。

secrets 上下文在 steps 的 if: 里不可用

官方的 Context availability 表里，jobs.<job_id>.steps.if 允许的是 github, needs, strategy, matrix, job, runner, env, vars, steps, inputs —— 没有 secrets。

写 if: secrets.X != '' 不报错，只是恒为空，那一步会 永远被跳过：「配好了却不发布」而且毫无提示，比直接失败更难查。 正确做法是在 job 级 env 里算一个旗标（那一层允许 secrets）， 步骤只看旗标。

  • 同一域名四种角色，替换目标各不相同

  • 散在 20 个文件里，比想象的多得多

这类脚本的规则表里必须逐条写着原始域名，否则认不出要替换什么。 也就是说脚本本身就是一份域名清单 —— 进了公开仓库等于把要隐去的东西直接 发出去。本项目实际踩过这一步：清理跑得很干净，却把清理器推上去了。

放仓库外，或让它从一个被 .gitignore 排除的规则文件里读。

替换后必须重跑测试 —— 占位符命名会影响断言数据
python3 tests/run.py                      # 必须仍全过
git status --short                        # 确认没有 config.yaml / .env
git ls-files | grep -iE 'scrub|domain'    # 清理器别在里面
占位符怎么取名会影响测试是否通过

这不是洁癖，是三条真实约束：

1 · 字母按原名字母序分配。有断言把运行时 sorted() 的结果和源码里的字面量比对，字母乱分配会让两边排序不一致 —— 测试失败， 而原因跟被测逻辑毫无关系。
2 · 短名 == 域名首标签。无别名表时的兜底匹配靠这个性质。
3 · 但有一对故意不共享子串。「必须靠别名表才认得」那条断言靠它。 只顾 2 不顾 3，那条断言就恒真而不再验证任何东西。

另外，测试里当作前缀误匹配反例的几个域名刻意不替换 —— 换成占位符后那条断言会恒真。

路由批量管理：为什么要自己做

CPAMP 只能一条一条改。而「同一网址的多把 Key 档位是否一致」 这个唯一重要的结构，在它的扁平分页表里恰好看不见。

问题：158 条上游，16 页，看不出结构

CPAMP 的「AI 提供商」页把所有上游拍成一张扁平表，默认 10 条一页。 158 条就是 16 页。它的表格没有多选列（ProviderTable 的 props 全是单行回调），后端 router.go 的 provider 段只有 GET / PUT / DELETE 三个动词、没有任何 bulk 路径。 它自己的「按结果应用」是 for 循环逐条 read-modify-write —— 每改一条都要 GET /config 再 PUT 回整个 158 条数组。

更要紧的是：翻 16 页也看不出「同一个网址下几把 Key 的档位一不一致」。 而这恰恰是最容易出错、后果也最重的地方。

这个分裂到底有什么后果

CPA 按层级调度：只取 priority 最高那一桶 （selector.go 的 availableAuthsFromPriorityBuckets 只收 bestPriority）。所以上图那 4 把 Key 里：

  • 350 那一条被永远优先抽中，先被打光配额；
  • 另外 3 把停在 147，要等 155 / 154 / 153 / 150 / 149 / 148 这些档位全部冷却之后才轮得到 —— 实质是冷备。

而这 4 条的 models、headers、proxy-url 逐字相同，唯独 priority 不同。它不是有意配置，是漂移。

实测对账（2026-09-10）：拿部署前后两份 config.yaml 逐组比对 —— 注入前 40 组 0 组分裂，注入后 3 组分裂。也就是说，这些分裂是本项目 自己在写入时造成的。根因见下一节。

根因：不变式在 assign_priorities 之后被破坏

assign_priorities 本身是对的：它按 host_of(base_url) 分组，同一 host 的所有 SectionPlan 复制同一个值。问题出在它之后：

  • 用户手工改优先级时，覆盖是按 rid = row.line_no 应用的 —— 而每把 Key 各占一行。改一把，这一把就与同站其余的分层了。
  • priority_collisions 只检测「不同 host 拿到同一个值」， 不检测「同一 host 拿到不同值」。于是不变式被破坏时，一条告警都没有。

已补 priority_split_within_host()，列为阻断级告警， 并接进写回前的两处校验点。

不做什么

批量删除没有做。删除不可逆，而且条目下标会随删除移位 —— 一次批量里前一个删除会让后一个的下标失效。要做必须单独一条路径、 单独的二次确认、并且以内容指纹而不是下标定位。 当前只提供批量启用 / 停用 / 统一优先级三项，都是可逆的。

systemd 守护进程（生产部署）
# 创建 systemd 服务
sudo tee /etc/systemd/system/upstream-importer.service <<'EOF'
[Unit]
Description=CPA Upstream Importer Web Service
After=network.target

[Service]
Type=simple
User=deploy
WorkingDirectory=/opt/upstream-importer
Environment="CONFIG_PATH=/opt/cpa/config.yaml"
Environment="CPA_RELOAD_CMD=systemctl reload cpa"
ExecStart=/usr/bin/python3.12 /opt/upstream-importer/web/run.py
Restart=on-failure
RestartSec=10

[Install]
WantedBy=multi-user.target
EOF

# 启动并设为开机自启
sudo systemctl daemon-reload
sudo systemctl enable upstream-importer
sudo systemctl start upstream-importer

# 查看状态
sudo systemctl status upstream-importer
防火墙配置

CentOS 9 默认启用 firewalld,需放行 8765 端口：

sudo firewall-cmd --permanent --add-port=8765/tcp
sudo firewall-cmd --reload

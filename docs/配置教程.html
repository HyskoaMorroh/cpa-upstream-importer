当前部署与验收边界

共享 VPS 的实际配置在 /opt/deploy：.env、docker-compose.yml、nginx.conf 由两个项目共用。保留另一项目的服务、网络、卷与变量，不能把仓库模板整份覆盖到生产。

请按本页步骤填写变量、核对挂载并拉取镜像。另附长篇教程中的历史排障数据和旧命令不是当前验收结果。请求数下降、容器 healthy、目录列出模型都不能单独证明速度提升或真实可用。

CPA api-key-usage 是历史请求统计，不是当前可调度账号清单。下游 schedulable 恢复必须核验部署版本对应的专用接口或批量字段；普通账号 PUT 不能作为恢复成功证明。公开源码中 TLS 指纹仅对 Anthropic OAuth/SetupToken 生效，未指定模板可使用内置模板；API key 同名字段不代表生效。

读懂探测次数与耗时

页面的“推理尝试”统计已记录的推理尝试，不包含模型目录等 HTTP 请求，也不包含发送前被策略拒绝的操作。显示 0 次时仍可能发生目录查询，需结合任务日志判断。

检测速度应分开看初始化、排队、目录查询、推理、定档和写回，并同时核对成功、失败及阻断数量。多线程任务不能按单项时间乘账号数估算；全部阻断的批次不能证明正常探测更快。请以同一镜像、相同配置与网络条件下的完整流程实测为准。

1. 从证据到配置

投喂台读取账号和现有配置，按协议探测、推荐模型与优先级，生成可核对的变更，再写回 CPA 配置。每一项结果都应说明依据；空白、待定或请求失败不能当作完成。

完整处理链

解析账号 → 受预算约束的探测 → 定档与模型证据 → 预览差异 → 写回与读回 → CPA 重载与业务验证

证据分层模型目录说明“存在候选”，请求成功说明“这个协议与凭据本次可用”，运行统计说明“历史健康状况”。三者不能相互代替，也不能仅凭模型名称宣称能力。

2. 共享部署与本地文件

VPS 实际运行目录为 /opt/deploy。外层配置与另一个项目共用；仓库内同名文件是独立模板。本地隔离测试副本只用于验收，不能整份替换共享生产配置。

部署关系图

GitHub 已审核源码 → CI / Docker Hub 镜像 → VPS importer

私有 .env + compose + nginx → importer ↔ 共享 CPA config.yaml

importer 与另一项目 → 已有 mihomo 服务及持久卷 → 上游

文件处理方式
审核后的源码、公共 README、公共教程提交 Git，由 CI 构建；不是整目录无筛选上传。
外层 .env、config.yaml、compose、nginx.conf私下维护 VPS 实际副本；只调整本项目相关部分，保留另一项目的配置。
mihomo-manager 脚本按镜像构建配置打包；订阅、密钥与实际代理配置独立保存。已有共享代理优先复用。
真实账号、MHTML、日志、备份、私人图文记录仅本地受控保存，排除 Git 和镜像构建上下文。
忽略规则不等于脱敏完成提交前检查已跟踪文件及 diff，构建前检查 Docker 上下文。已跟踪的敏感文件不会因新增 .gitignore 自动消失。不要公开原始诊断输出或浏览器截图。

3. 填写环境变量

编辑外层私有 /opt/deploy/.env，保留已有键，只更新对应值，避免反复追加重复定义。口令在本地生成并私下保存，不粘贴到报告或命令历史。

变量 / 配置填写与核对
外层 compose 的配置挂载源当前使用 ./config.yaml；compose 位于 /opt/deploy 时对应 /opt/deploy/config.yaml。修改宿主机路径应调整 volume 的源文件，并确认与 CPA 读取源一致。当前外层 compose 不引用 CONFIG_PATH，在外层 .env 添加它不会改变挂载。
CONFIG_PATH（仓库独立模板）仅独立 compose 用它指定宿主机配置绝对路径，例如 /opt/deploy/config.yaml；不要与外层部署混用。
IMPORTER_CONFIG / --config镜像入口用 IMPORTER_CONFIG 指定容器内路径，当前为 /data/config.yaml，再传给 server.py --config。直接运行 Python 必须显式传 --config；它不会自动读取 .env 的 CONFIG_PATH。
IMPORTER_TOKEN建议固定的随机强口令。留空可能生成临时口令并出现在私有日志中，不适合稳定运维。
CPA_MANAGEMENT_PASSWORD外层部署使用的 CPA 管理明文口令；compose 必须映射为 importer 容器内 CPA_MANAGEMENT_TOKEN。不要填 bcrypt 哈希。
CPA_MANAGEMENT_TOKEN仓库独立模板直接使用此变量；不要误以为外层同名变量一定生效。
CPA_UPSTREAM_URL容器能够访问的 CPA 地址，例如 http://cli-proxy-api:8317；以实际网络服务名与端口为准。
IMPORTER_UID / IMPORTER_GID确保容器用户拥有配置文件及写回所需目录权限。属主相同是常见办法，不是唯一办法；不能只检查数字是否相等。
IMAGE / PULL_POLICY按外层 compose 的实际变量选择已验证镜像标签或 digest；独立模板默认 Docker Hub 镜像、always 拉取策略。
IMPORTER_PROBE_LEDGER置于持久化可写备份卷；不可写会拒绝主动请求。
MIHOMO_SUB_* / MIHOMO_SECRET新建独立代理才按模板配置订阅；复用共享代理时保留其现有订阅、控制器鉴权和网络配置。

外层 .env 填写示例

下列仅为 importer 使用的条目。逐项合并到现有文件，替换占位口令，保留另一项目的全部变量。UID/GID 按配置文件及备份卷实际权限填写；首次创建备份卷后也需核对可写权限。

私有 .env 示例：占位值必须替换
IMPORTER_TOKEN=REPLACE_WITH_RANDOM_IMPORTER_TOKEN
CPA_MANAGEMENT_PASSWORD=REPLACE_WITH_CPA_PLAINTEXT_PASSWORD
IMPORTER_UID=0
IMPORTER_GID=0
IMPORTER_PROBE_MODE=managed
IMPORTER_PROBE_POLICY_FILE=/backups/probe-policy.json
IMPORTER_PROBE_LEDGER=/backups/probe-policy.sqlite3
CPA_SOURCE_CACHE_DIR=/backups/source-cache
IMPORTER_LOG_LEVEL=INFO
IMPORTER_LOG_TO_FILE=1
IMPORTER_MEMORY_LIMIT=1G
PROBE_PROXY=http://mihomo:7890

当前共享 compose 的 importer 镜像、CPA_UPSTREAM_URL 和 DRIFT_PROXY 是服务内固定值；外层 .env 新增 IMAGE、PULL_POLICY、CPA_UPSTREAM_URL 或 DRIFT_PROXY 不会覆盖它们。更换镜像 digest 或地址应修改对应服务字段。CPA_MANAGEMENT_PASSWORD 要与 CPA 当前明文管理口令一致，不能复制 secret-key 的哈希。

4. 核对 compose 挂载与网络

外层服务名为 upstream-importer，仓库独立模板为 cpa-upstream-importer。命令必须对应所用文件。当前 VPS 只拉取已发布镜像，不上传私密源码、不执行源码构建，也不要用仓库模板覆盖共享主栈。编辑外层 .env 时修改已有条目，避免追加同名变量。确认配置挂载可读写，备份卷与账本持久化，CPA、nginx、mihomo 与 importer 之间网络可达。

源码规则缓存：更新失败时保留最近成功版本

在 importer 服务的 environment 中设置 CPA_SOURCE_CACHE_DIR: "${CPA_SOURCE_CACHE_DIR:-/backups/source-cache}"，并保留现有 /backups 持久卷。共享主栈与独立模板均已配套此默认值；默认部署无需重复追加外层 .env。自定义路径时，修改已有变量并确认目标位于可写持久卷内。

离线回退 ≠ 最新规则 每次启动仍尝试在线同步；失败后只读取与当前仓库引用和提取规则匹配的最近成功快照。页面应显示陈旧状态、年龄和失败原因。没有缓存、缓存损坏或规则不匹配时，应明确缺少证据，不能显示绿色一致。源码缓存不能代替模型实际探测。

在隔离环境中先在线同步一次，再检查断网回退与容器重建后的缓存保留。不要清空真实探测账本。直接运行源码时，需显式设置 CPA_SOURCE_CACHE_DIR 才开启磁盘缓存。

使用 config --quiet 检查语法，避免普通 config 把展开后的密钥打印出来。仅更新 importer 时不要重建共享代理或另一项目；若本次同时更新代理初始化或健康检查脚本，请按下方共享 mihomo 升级步骤安排维护窗口。
仅检查外层部署文件，不启动或修改服务
docker compose --env-file /opt/deploy/.env -f /opt/deploy/docker-compose.yml config --quiet

共享 compose 的 importer 配置片段

这是字段核对片段，合并到已有同名服务，保留原健康检查、资源限制、安全选项及依赖；不要新建重复 services 或覆盖整份共享文件。CPA 与 mihomo 须同在共享栈的 default 网络，备份卷沿用已有名称。

只核对并合并 importer 服务字段
services:
  upstream-importer:
    image: swhesong/cpa-upstream-importer:latest
    pull_policy: always
    ports:
      - "127.0.0.1:8765:8765"
    user: "${IMPORTER_UID:-0}:${IMPORTER_GID:-0}"
    environment:
      IMPORTER_HOST: "0.0.0.0"
      IMPORTER_PORT: "8765"
      IMPORTER_CONFIG: "/data/config.yaml"
      IMPORTER_BACKUP_DIR: "/backups"
      IMPORTER_TOKEN: "${IMPORTER_TOKEN:-}"
      CPA_UPSTREAM_URL: "http://cli-proxy-api:8317"
      CPA_MANAGEMENT_TOKEN: "${CPA_MANAGEMENT_PASSWORD:-}"
      IMPORTER_PROBE_MODE: "${IMPORTER_PROBE_MODE:-managed}"
      IMPORTER_PROBE_POLICY_FILE: "${IMPORTER_PROBE_POLICY_FILE:-/backups/probe-policy.json}"
      IMPORTER_PROBE_LEDGER: "${IMPORTER_PROBE_LEDGER:-/backups/probe-policy.sqlite3}"
      CPA_SOURCE_CACHE_DIR: "${CPA_SOURCE_CACHE_DIR:-/backups/source-cache}"
      PROBE_PROXY: "${PROBE_PROXY:-http://mihomo:7890}"
      DRIFT_PROXY: "http://mihomo:7890"
    volumes:
      - ./config.yaml:/data/config.yaml:Z
      - importer-backups:/backups:Z
    networks:
      - default
volumes:
  importer-backups:

宿主机 config.yaml 必须预先存在且为文件，并与 CPA 的配置挂载指向同一文件。仅给 importer 挂所需文件；不要挂整个 /opt/deploy。SELinux 的卷标签须结合共享读取策略核对，不要为了排错反复重标记另一项目的目录。

5. 入口与轮询

宿主机 nginx 可指向已绑定的回环端口；容器 nginx 的 127.0.0.1 指向自己，通常应通过共同网络访问 importer 服务。核对路径转发、登录鉴权、CSP connect-src、请求体大小与轮询响应。

长任务应快速返回任务标识，浏览器随后轮询进度。增大 nginx 超时不能修复 JavaScript 异常、401/403、CSP 阻止、后端 500、任务丢失或网络断开。先查看失败请求的状态码与脱敏错误类别，再调整对应配置。

宿主机 nginx 的同源入口

以下为独立入口示例。共享部署时，只将所需指令合并到现有、已配置 HTTPS 的 importer 专用 server 和 location 中，保留证书、访问控制、根路径已有的 limit_req 限流，以及现有 proxy_connect_timeout、proxy_read_timeout、proxy_send_timeout 设置；示例中的超时数值不应覆盖现有配置。已有登录鉴权、写回和轮询专用 location 也须保留，不要整块替换。根路径转发保留 API 路径，避免为前端另外拼接跨域地址。其他业务 server 块保持原样。

宿主机 nginx：合并到已有 importer server
location / {
    proxy_pass http://127.0.0.1:8765;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    client_max_body_size 16m;
    proxy_connect_timeout 10s;
    proxy_read_timeout 120s;
    proxy_send_timeout 120s;
    proxy_buffering off;
}

若 nginx 在容器内，同网络下将 proxy_pass 改为 http://upstream-importer:8765；不能使用容器自身回环。已有 CSP 的 connect-src 应允许 'self'，并在浏览器网络面板核对请求确实同源。先执行 nginx -t，检查通过后再按既有运维流程重载 nginx；不要用重载来掩盖后端错误。

6. 复用 mihomo

保留已有共享 mihomo 的服务、订阅、控制器密钥和持久卷，确认 importer 使用正确的容器网络地址。仓库可选 mihomo profile 提供独立部署引导，不能因此在共享栈重复启动一套代理。

通用连通性检查仅说明代理出口能访问那个测试地址；不能证明目标站点凭据、模型或协议可用。目标明确拒绝、限流或限制客户端时，应显示原因并遵守探测策略，不能靠换代理重置预算。

代理变量如何对应实际流量

共享代理地址：合并已有 .env 条目
PROBE_PROXY=http://mihomo:7890
MIHOMO_SECRET=REPLACE_WITH_EXISTING_CONTROLLER_SECRET
MIHOMO_SUBSCRIPTIONS=provider1=https://subscription.example/subscribe?token=REPLACE_ME

复用已有 mihomo 时，上面控制器密钥和订阅必须保留现有真实值，不要换成示例。订阅也可采用已有 MIHOMO_SUB_* 条目；二者同名时后者优先，不要同时新增重复 provider。密钥用于控制器鉴权，不是代理 URL 的密码；订阅 URL 只交给现有初始化服务，不能写进公开教程、日志或 Git。

位置用途
PROBE_PROXYimporter 探测候选代理，可逗号分隔。共享服务地址通常是 http://mihomo:7890。
DRIFT_PROXY（compose environment）源码规则同步所用代理；当前共享部署在服务内固定配置。
config.yaml 中 proxy-urlCPA 实际转发所用条目代理。必须从 CPA 容器可达，不能把 Windows 本机地址照抄到 VPS。

config.yaml：先保留原配置，再审查方案差异

以下仅展示支持的 OpenAI 兼容段结构，不是完整 CPA 配置，不应直接投入生产。保留原配置的端口、管理鉴权、其他协议段和注释。占位模型需替换为该凭据实际验证通过的上游模型 ID。

结构示例：由预览核对模型、凭据与代理
openai-compatibility:
  - name: example-provider
    base-url: "https://api.example.com/v1"
    priority: 100
    api-key-entries:
      - api-key: "REPLACE_WITH_PRIVATE_UPSTREAM_KEY"
        proxy-url: "http://mihomo:7890"
    models:
      - name: "REPLACE_WITH_VERIFIED_MODEL_ID"
        alias: "REPLACE_WITH_CLIENT_MODEL_ALIAS"

name 标识提供方；base-url 填兼容接口基址；models.name 为上游实际 ID，alias 为客户端请求名。priority 是路由优先级，不代表模型高低档或能力评分；不要凭模型名称猜测定档。api-key-entries 内的 proxy-url 只作用于对应凭据，直连条目应按已有方案处理，不要给所有条目统一补代理。其他协议段字段位置不同，不可直接套用此片段。

操作顺序：备份真实文件 → 用私有副本挂载测试 → 读取现有路由 → 完成探测与定档 → 逐条查看写回差异 → 执行写回 → 检查 CPA 重载与真实调用结果。待定、预算耗尽、断网、空白证据均不构成成功依据；不能靠手填示例 priority 或模型列表绕过验证。

先保留私有配置备份，确认 CI 成功、标签或 digest 对应待验收提交。默认分支更新 latest；功能分支通常有独立标签。以下仅更新 importer，保留共享依赖。

在 VPS 上执行；更新前核对外层 .env 的镜像配置
docker compose --env-file /opt/deploy/.env -f /opt/deploy/docker-compose.yml pull upstream-importer
docker compose --env-file /opt/deploy/.env -f /opt/deploy/docker-compose.yml up -d --no-deps upstream-importer
docker compose --env-file /opt/deploy/.env -f /opt/deploy/docker-compose.yml ps upstream-importer
docker compose --env-file /opt/deploy/.env -f /opt/deploy/docker-compose.yml images upstream-importer
健康检查不是业务验收容器 healthy 只证明检查端点响应。还须核对实际镜像 digest、前后端版本一致性，并在真实网页完成下面四条流程。本地测试应使用真实配置的私有副本、真实账号与相同挂载方式，避免改坏生产基线。

8. 主动探测策略

IMPORTER_PROBE_MODE=managed 为默认主动模式，不要求额外许可文件；passive 只解析和分析，不发上游请求。可选 IMPORTER_PROBE_POLICY_FILE 用于站点覆盖；一旦设置有效覆盖文件，未列出的站点不探测，格式错误则拒绝请求。

目录查询、生成、能力检查、重试和代理请求共享预算；同站多 Key、重复任务、重启不会自动清除持久账本。明确拒绝或限流必须显示真实终态。不要发送问候、身份询问等无效测试文本，也不要把未实测改成通过。

任务并发与单站并发分别控制

站点覆盖规则可选填 max_inflight，取值为 1～64 的整数，控制同一 provider 同时占用的请求槽位。同服务的别名规则必须填写一致的限额。已有覆盖规则未填写时保持上限 1；明确填写 1 仍串行；系统托管规则默认上限为 4。

同一凭据跨协议与别名仍串行，不同凭据才在共享上限内并行。页面任务并发数、主机限制、请求间隔、预算及停止状态共同约束实际请求；提高并发上限不会增加预算，也不能解除历史请求结果待核对的暂停。多实例共享账本时，无法证明归属的活动预约仍会暂停新请求。

验收速度以整批任务各阶段的实际起止时间为准，同时核对真正发出请求的数量、成功数、失败数和策略阻断数。不要把并行请求耗时相加估计整批时间，也不要把很快结束的全阻断任务当作性能通过。

普通 403 / 429 停止该站本次任务，按 Retry-After 或默认 900 秒保持跨任务冷却。到期后新任务才能重新核实；显式禁测、封禁或指定客户端拒绝持续停止，不通过换 Key、代理或重启清除。页面没有已验证的手动取消接口。轮询中断时不要重复提交，先恢复同一任务状态；关闭或刷新页面不能视为取消后端任务。未完成项目不得标为成功。

探测中断后：先核对账本与结算凭证

“历史请求结果待核对”或“预约执行者未知”表示某次请求的最终结果仍不确定，相关上游暂停新的探测。刷新、重复提交或重启容器不会自动解除暂停。

成对持久化与备份：探测账本与同目录的结算凭证数据库一起保留；后者的文件名是在账本文件名后追加 .settlements.sqlite3。升级保留整个持久化目录，不要只迁移一个数据库，也不要删除、清空账本或改挂空目录。备份前停止新探测并等待运行任务结束，使用一致快照；SQLite 写入期间直接复制单个数据库文件可能遗漏尚未归并的数据。恢复使用同一时点的成对备份。

  1. 在原实例查看原任务状态和脱敏日志，确认是否仍在执行；避免多个实例重复提交同一上游。
  2. 核对强制终止、重启或迁移记录，检查原持久化目录和配套结算凭证是否完整挂载。
  3. 有匹配的完整结算凭证时，系统读取策略账本并校验签名、预约与执行身份后恢复结算；校验失败继续暂停，应核对备份及存储完整性。
  4. 凭证缺失时继续核对原实例日志、任务结果及上游请求或用量记录。等待很久、没有运行任务或容器已重启均不能证明旧请求没有执行。当前版本没有跳过核对的一键解锁，缺失结果的预约仍保持暂停。
恢复不等于探测通过中断恢复不解除已确认的上游使用限制，不重置冷却或历史记录。旧版本缺少证据的限制标记按既有受控恢复规则处理，不应手工改成可用。结果未知不能计为探测、定档或写回成功；验收保留受影响范围和未完成原因，待实际执行及独立结果核对完成后再更新结论。

9. 四条流程逐项验收

① 添加账号：从投喂到写回

在投喂输入框粘贴账号文本，先点解析（零请求），核对识别数量、重复项和协议归属。按上一节设置主动探测策略与预算，再点开始探测。等待任务结束，逐站查看参数来源、模型选择和定档结果；无法解释的待定或失败项先排查。

确认需要的条目与模型后，点生成写回方案。逐项核对差异和校验结果；有有效变化且校验通过时，才点确认写回。最后分别查看本地写入、配置读回、CPA 重载和业务验证结果。某一项成功不代表其余环节已成功。

② 路由批量管理：先选范围，再看差异

展开路由批量管理，点重新读取取得当前配置。筛选并选择目标分组；“选中筛选结果”会选择当前筛选范围，操作前核对数量。按需要统一优先级、启用、停用或编辑分组参数，再点预览并写回这些改动。确认差异只涉及目标分组后，点本面板的确认写回并检查回执。删除有独立确认步骤，应单独核对目标。

③ 全局调优体检：逐项理解建议

展开全局调优体检，点开始体检。阅读当前值、建议值与原因，再检查生成的配置差异。有可应用方案时，核对后点本面板的确认写回；没有变化时无需写回。完成后检查回执并重新体检，确认实际配置与预期一致。

④ 全量重探：只检查现有配置时保持输入为空

保持投喂输入框为空，勾选全量重探，等待界面读取已有配置数量，再点开始探测并核对弹出的确认说明。如果同时输入新账号，任务范围会包含这些输入，不能再当成只检查现有配置。探测策略和预算仍然生效。

任务结束后逐站检查终态，特别查看停用项、模型变化及代理和请求头的证据。接着依次完成生成写回方案 → 核对差异 → 确认写回 → 检查回执。已有任务未结束时，先通过接回任务恢复进度，避免重复提交；已确认写入后若重载失败，应处理重载结果，不要盲目重写同一方案。

流程必须看到的证据写回后再查
① 投喂 → 写回解析数量与去重理由；协议探测终态；参数和依据；高低模型选择；定档；完整 diff。只出现预览中的条目；原注释和无关配置保留；读回、CPA 重载、业务验证分别有结果。
② 路由批量管理选择范围清楚；同类型同域名一致、不同域名区分；停用、代理和模型变更均可预览。只改选定范围；关联域名约束正确；失败时有明确原因与恢复路径。
③ 全局调优体检基于当前配置解释建议值、请求预算与回源时间；每项调整均有差异。只修改已确认的全局键；未知字段、另一项目配置与已有注释保留。
④ 全量重探包含已有停用项；每站有进度、终态、证据与写回方案；失败/预算不足不混成成功。逐项审查重新启用和模型变更；完成预览、写回、读回、重载，并核对未成功项目仍有明确标记。
不接受的结果黑屏、空白参数、无法解释的默认勾选、定档失败、一直待定、轮询无响应、写回后无读回证据。遇到这些情况，当前方案不能视为可用配置。记录任务标识和错误类别，修复后从相应步骤复验。

批量管理必须同时核对当前筛选范围、全部已选数量和筛选外已选数量。筛选后不要假设旧选择已消失；以预览中实际目标为准，发现非目标组先清除并重新选择。

10. 模型与 priority 的判定

模型来源须标明目录、配置、权威名录或实测。版本按系列和代际理解，不能用字符串排序取一个最高名称。保留需求规定的最新与上一代同档变体，并排除 mini、flash、fast 等低档类别；计算档变体和协议归属需分别判定，不能跨段混入不支持的模型。

最新代不可用时，应分别展示“最新目录候选”和“已验证的最高可用代际”，不能把候选写成已验证。目录缺失或探测受限应说明原因，不用空白或无依据的全选掩盖。

策略预选与写回证据分开显示：最新代及上一代高端候选可以按策略预选，但没有对应协议的成功请求证据时，不能用候选替换已有模型列表。原模型和参数的保留原因应出现在结果或差异说明中；没有可用新证据就保留原记录。停止任务意味着停止继续安排请求，已经完成的证据仍保留，不能把中止标成探测成功。

同类型同域名各 Key 共用 priority，不同域名需要区分。CPA 的排序语义应以实际实现核对；不能照搬其他项目方向相反的优先级数字。健康信息缺失须说明证据不足。停用项重新探测后，重新启用也应出现在预览中，由写回操作落实。

共享 mihomo：升级镜像后刷新初始化脚本

两个项目一起受影响先完成正在运行的探测和写回，再安排维护窗口。重新创建 mihomo 会同时短暂中断两个项目的代理连接。不要删除共享卷，不要另起同名代理。

在 VPS 实际部署目录操作。仅更新 importer 不会刷新既有代理卷里的健康检查脚本；先重新运行初始化服务，确认成功后再更新代理和 importer。

cd /opt/deploy
docker compose pull upstream-importer mihomo-init mihomo
docker compose up -d --force-recreate mihomo-init
docker compose logs --tail=80 mihomo-init

确认初始化服务成功退出且日志显示自举完成后，再执行下一组命令。若初始化失败，先排查订阅、权限和镜像，不要继续重建代理。

docker compose up -d --force-recreate mihomo
docker compose up -d --no-deps upstream-importer
docker compose ps mihomo upstream-importer

MIHOMO_IMAGE 必须使用包含初始化脚本和代理二进制的本项目镜像。若单独固定了代理镜像版本，应同步更新。正常升级不要设置 MIHOMO_FORCE_REBUILD=1，它会重新生成代理配置。升级后分别检查两个项目的真实代理请求和 importer 的 CPA 管理连接；healthy 仅代表健康检查通过。实际共享配置文件保留在部署目录，不随源码提交。

11. 探测速度、节拍与可排查日志

本章对应 2026-10-13 的一组改动。它们改变了默认行为，所以升级镜像后界面与日志的表现与旧版不同；逐项说明依据与验收方法。

同站间隔改为自适应：留空即可

投喂页的「同站间隔」输入框默认留空，占位文字为「自适应」。留空时后端从一个乐观起点开始发请求，撞上限流再按阶梯退避并记住该站的节奏；填写数字则视为操作员指定的地板，自适应只会在它之上加，不会降到它以下。填 0 与留空不同：前者是「明确要求零间隔」，后者是「交给自适应」。

旧版把这个框硬写为 3，而那个 3 秒来自某一个站的 bulk probe guard 实测值，被当成所有站的起始节拍，同时又因为「学到的值只升不降」而成为地板。代价在同域名多凭据场景下最明显：同一主机的多把 Key 会把每次请求都垫上 3 秒。

输入后端行为适用情形
留空（默认）乐观起点 + 撞限流阶梯退避 + 记住该站节奏绝大多数情形
填数字该值作为地板；正文里读不出阈值时不凭空放慢已知站方节奏阈值，或要复现旧节拍
填 0零间隔，仍受站点预算、账本与并发约束确认过站方无限频时的临时压测
自适应不等于无限制节拍只是三道闸中的一道。账本预算、同服务商在途上限、页面并发数仍然生效；同一服务商的多把 Key 在账本层面始终串行（持久账本的在途位是单一字段），所以界面上同域名批次常显示「在飞 1 个」，这是预期行为而非卡住。

限流信号的识别范围扩大

旧版只认正文里带 bulk probe 字样的「限频」。HTTP 429 被归入「临时」类、「限流」是另一类，两者都不会触发节奏学习。配合乐观起点后这个缺口会放大，所以现在三类信号都会喂给学习器：「限频」、「限流」、以及 HTTP 状态 429。

「临时」类里真正的瞬时故障（状态 000、连接中断）不触发退避 —— 那不是「你太快了」，退避只会让一次偶发故障拖慢整批。

正文里带确切阈值（例如「N 个模型 / W 秒」）时按阈值算平均间隔并留余量；读不出阈值时按固定阶梯爬一档，每撞一次升一级，升到上限即止。事件流里会出现 rate-limit-learned，其中 source 字段区分 site-threshold（读到站方阈值）与 backoff-ladder（没读到，按阶梯）。

站方属性跨凭据复用一次实测

静默换模与上下文窗口量的是站方自己的配置，不是某一把 Key 的属性。所以同一站、同一段、同一模型只实测一次，其余凭据复用该结论；事件流里对应 swap-reused 与 context-reused，措辞明写「复用本轮同站同段同模型的实测，未重复发请求」。

上下文窗口这一项最贵 —— 每段数次大体积请求 —— 复用省下的请求最多。复用缓存只在一轮任务内有效，不落盘：站方随时可能改配置，跨任务复用等于把旧结论当新证据。

凭据相关的结论不复用「这把 Key 能用哪些模型」仍然逐个凭据验证。同址不同凭据可能权限或渠道不同，一把 Key 的成功不能替另一把作证 —— 这条约束没有放宽。没测出数的结果（例如上游未统计 token 导致窗口不可信）也不入缓存，后续凭据仍可重试。

跨站并发按实际站数自适应

勾选「并行探测」时，前端不再固定下发跨站并发数，由后端按本批真实站数与上限取小。不同站之间没有互相等待的理由：节拍与预算都按站分桶，跨站并发对任一单站的请求频率没有影响。

单个候选内部的分段并行度仍是 4（四段到顶）。关掉「并行探测」则退回完全串行，用于撞上「按账号而非按端点」限频的站。

验收口径速度要看整批的实际起止时间，并同时核对真正发出的请求数、成功数、失败数与策略阻断数。请求数下降不等于更快，全部被阻断的批次结束得最快但什么都没验证。推荐用持久账本里预约的时间跨度除以预约总数，得到「每次请求的实际成本」，再与站方的实测往返延迟比较：两者接近说明等待已被压掉，差距大说明时间花在自己的等待上。

探测过程落进日志（排查的前提）

旧版的事件流只存在于浏览器里：IMPORTER_LOG_LEVEL=DEBUG 与 IMPORTER_LOG_TO_FILE=1 全开时，一整轮探测在磁盘上也只留下一行汇总。浏览器一关、容器一换就什么都不剩，而部署方式是「VPS 只拉镜像」且 pull_policy: always 每次都会重建容器。现在每条事件同时写一条 DEBUG 日志，带任务号前缀便于在交织的日志里按任务分离。

收集探测日志（在 /opt/deploy 执行）
# 实时跟随（容器标准输出）
docker compose logs -f --tail=200 upstream-importer

# 导出最近一段到文件，便于附在排查记录里
docker compose logs --no-color --since 30m upstream-importer > /tmp/importer-30m.log

# 落盘日志（IMPORTER_LOG_TO_FILE=1 且挂了日志卷时）
ls -la ./logs/upstream-importer/
tail -n 300 ./logs/upstream-importer/importer-*.log

# 只看探测判定（按任务号过滤，xxxxxxxx 换成实际前缀）
grep -E '\[[0-9a-f]{8}\] (attempt|catalog|prescan|section-done|candidate-)' \
  ./logs/upstream-importer/importer-*.log | tail -n 200

日志里的网址只保留可区分的词干，不写完整私有域名；凭据与 Authorization 不进日志。字段按白名单输出 —— 新增字段默认不记录，避免将来加字段时漏掉一次脱敏判断。日志目录通常是 bind-mount 出去的，这两条约束是必要的。

这条日志能回答什么每站每段「探了没有、发了几次、什么状态、被哪条策略挡住」。例如 prescan ... status=blocked probe_policy_code=provider_stopped 直接说明本轮一个请求都没发，原因是持久账本里的停止记录，而不是网络或凭据问题 —— 这类结论过去只能靠猜。

旧版限制记录的有界复核

持久账本里的限制证据带分类器版本号。当判定逻辑本身发生语义变更时，版本号会递增，低于当前版本的证据不再单独构成永久封锁，可以走已有的有界复核路径；当前版本的证据语义不变，仍是永久结论。

这解决的是一类具体情形：某条记录是在工具自身请求形态有缺陷时产生的，修正形态后同一个站实际可用，但旧记录仍在封死整站 —— 此时光升级镜像救不回来。复核不是放行：仍需显式任务作用域、仍受预算与冷却约束，仍要一次真实请求来确认，失败即回到停止状态。旧证据行本身不被删除或改写，审计链完整。

不要据此手工改写账本复核由策略引擎在满足条件时自行发起。直接编辑或删除账本会破坏结算凭证的配对关系，使正在等待核对的预约无法恢复。确认某个服务商是否仍被停止，查账本里的停止状态与证据版本，不要以「换了 Key 还是不通」推断。

12. 两类「看着像站坏了」的卡点

本章两件事都来自 2026-10-14 的本机实跑。它们的共同点是：界面显示站不可用，而站本身是好的 —— 真因在账本状态或站方的提示没被读懂。先按这两条排除，再去怀疑凭据和网络。

探测一次请求都不发：先看在途预留

症状：点检测后很快结束，推理尝试 0，日志里只有一行 probe_policy_code=orphaned_inflight，界面提示「N 个未结算请求的持有者无法确认」。涉及的服务商没有被判死（停止状态是空的），但一个请求都发不出去。

成因是容器在探测途中被重建。任务状态只在内存里，正在途的预留没有人结算；这类预留如果连签名结算凭证都没来得及写（请求已发出、结算前进程被杀），重启后的自动重放无从恢复，而判活依据是进程内的持有者登记表 —— 重启后必然为空。于是这些预留永久停在「归属无法核实」。

这与部署方式直接相关：镜像配置是每次 up -d 都重建容器，所以正跑着全量重探时拉新镜像就会留下这类残留。

要确认的事怎么看
有没有孤儿预留界面提示文案，或 /api/context 的 probe_policy.orphaned_inflight_count
是哪些、什么类型同一处的 probe_policy.orphans：每条给出预留与服务商标识前缀、预留时间、请求类型、有没有结算凭证
能不能自动恢复has_settlement_payload 为真表示本该被自动重放恢复；仍在列表里说明凭证校验没过（账本被换或文件损坏），那是另一类问题
没有「一键解锁」，这是刻意的请求可能真的已经发到上游并计了费。自动按超时清理会掩盖真实用量，还可能让同一次请求被重复发送。所以必须先去核对原请求到底有没有执行 —— 查原实例日志、上游用量或调用记录 —— 再把结论如实记进账本。
核销一条孤儿预留（先核对，再记账）
# 1) 列出孤儿预留（只读，不改任何状态）
curl -s -H "Authorization: Bearer $IMPORTER_TOKEN" \
  http://127.0.0.1:8765/api/context | python3 -m json.tool | \
  grep -A 20 '"orphans"'

# 2) 核对那次请求到底有没有执行（原实例日志 / 上游用量记录）
docker compose logs --no-color upstream-importer | grep -i '<预留前缀>'

# 3) 按核对结论记账。outcome 只接受 executed 与 not-executed；
#    note 必填，会写进审计留痕。
curl -s -X POST -H "Authorization: Bearer $IMPORTER_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"confirm":true,
       "reservation":"<预留前缀>",
       "outcome":"not-executed",
       "note":"已核对原实例日志，该请求未到达上游"}' \
  http://127.0.0.1:8765/api/orphan-settle

核销只释放被占住的在途位，不解除任何既有的服务商限制或冷却。记账结果会标成人工核对（与引擎自己的结算可区分），依据原文进审计留痕。缺 confirm、outcome 取值不对、没写依据、标识格式错，四种情况都会被拒绝。

站方在失败正文里指名了另一个模型

有的中转站把某个协议段的模型换了名字，并把正确用法写在失败响应的正文里。实测遇到的一条（claude 段）：

HTTP 400 的响应正文（站方自己的说明）
由于 claude 模型供应难以保证，上线 gpt-6-astra-cc-format 模型，
支持 messages 格式，通过 claude --model 'gpt-6-astra-cc-format[1m]' 使用该模型

也就是说这个站的 claude 段没有真正的 claude 模型。工具现在会从这类正文里读出站方指名的名字（支持 --model '名字' 与「上线 某名字 模型」两种措辞），插队试一次，并在事件流里记一条 站方指名改用 …。

两个边界值得知道：

  • 只跟随一次。替代模型的响应里可能又提另一个名字，无限跟随会变成被正文牵着走的请求放大器。
  • 只认正文里写出来的名字。不猜、不拼接；过短或含路径分隔符的一律丢掉。正文没点名就一发都不多打。
名字里的方括号后缀是客户端语法，不是 HTTP 字段上面那条里的 [1m] 是 claude 命令行的写法，由命令行翻译成请求头。实测把它原样写进请求的 model 字段仍然失败；真正起作用的是 anthropic-beta 里对应的那一项。工具会把已知后缀剥掉并交给画像梯补对应的头，所以写回配置里的模型名是不带后缀的那个。

同一个段里不同模型可能返回不同的失败正文：一个说「换用某模型」，另一个说「请启用某能力」。两条都要读原文 —— 只看归类会把前者那句指示整个丢掉。排查时请对照事件流里每个模型各自的状态与正文摘要，而不是只看段级结论。

429 与 503 不是「这个模型不可用」

这两种响应表示请求已经过了站方的门禁、转发到上游后遇到忙或限流。它们属于可重试类：同一个模型稍后或换一把凭据可能就通，所以不应据此把模型或段判死。

与之相对，配额与门禁类的响应（例如明确说没有该模型、要求开通某能力、凭据无权）换时间重试没有意义，需要改模型名、补参数或联系站方。

收到 429 后账本会进入冷却这是设计行为：收到限流就停手一段时间，避免把站打得更死。此时紧接着重跑会被账本挡住并提示剩余秒数 —— 那不是修复没生效，而是冷却还没过。复测前先确认冷却已清零（界面提示或 /api/context 的策略摘要），否则会把「冷却中」误读成「改动无效」。

共享部署的 CPA 管理口令映射

外层 .env 使用 CPA_MANAGEMENT_PASSWORD，映射到 importer 的 CPA_MANAGEMENT_TOKEN。同一部署中的 cpa2sub2api 使用 CPA_MANAGEMENT_KEY；共享 compose 的映射为 ${CPA_MANAGEMENT_KEY:-${CPA_MANAGEMENT_PASSWORD:-}}。显式填写非空 KEY 时优先使用，否则复用 PASSWORD。两者均为空时必须补齐配置；不要填写 bcrypt 哈希，也不要将真实口令写入教程或提交记录。

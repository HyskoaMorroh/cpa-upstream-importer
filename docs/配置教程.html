1. 这个工具做什么

CPA（CLIProxyAPI）用一份 config.yaml 管理多个上游中转站。手工维护那份文件有三个难点：站点可不可用要逐个试、每个站支持哪些模型要逐个查、优先级要在几十个站之间统筹。这个工具把这三件事自动化。

一次完整导入经过四步
  1. 解析 —— 把 URL,密钥 的文本解析成结构化条目，去重、校验格式。
  2. 探测 —— 对每个站的每个段（codex / claude / gemini / openai-compatibility）真实发请求，判断可不可用、支持哪些模型、需要哪些请求头。
  3. 定档 —— 根据探测结果计算 priority、权重、前缀、代理、请求伪装等全部参数，生成写回方案。
  4. 写回 —— 行级编辑 config.yaml，保留原有注释与格式，写前备份、写后校验并通知 CPA 重载。
和 CPA / CPAMP 的关系 CPA 与 CPAMP 由其他作者维护，本项目不修改它们，只负责往 config.yaml 里写正确的数据。所以模型清单、请求形态这些会随 CPA 升级而变的东西，本项目都从 CPA 源码在线解析获取，不写死在代码里。

2. 文件分工：哪些上传 VPS，哪些只在本地

这一节最容易搞混。本项目目录里也有 docker-compose.yml / .env / config.yaml，但它们只是模板，不是 VPS 上实际执行的那份。

文件去向作用
upstream-importer/ 整个目录构建镜像源码。推到 GitHub 后由 CI 构建并推送 Docker Hub
.env（部署目录下的）上传 VPS令牌、密码、订阅地址等全部机密
docker-compose.yml（部署目录下的）上传 VPS服务编排：镜像、端口、挂载、依赖
nginx.conf（部署目录下的）上传 VPS反向代理、超时、限速、CSP
config.yaml（部署目录下的）上传 VPSCPA 的真实配置，被本工具读写
upstream-importer/mihomo-manager/打进镜像代理引导脚本，不单独上传
项目自带的 compose / .env / config.yaml仅本地本机调试模板，不上传
绝不能提交到 GitHub 的东西 真实 config.yaml、真实 .env、机场订阅地址、API 密钥、真实上游域名、个人路径、手工排查记录。仓库里已经用 .gitignore 与 .dockerignore 双重排除，提交前再跑一次 python tools/scrub.py --check 复核。

3. 配置 .env：逐项说明

VPS 上 /opt/deploy/.env 里与本工具相关的变量。没有默认值的必须填。

变量必填说明
IMPORTER_TOKEN可选前端登录令牌。不填时用 CPA 后台管理密码登录
CPA_MANAGEMENT_PASSWORD必填CPA 管理密码。两个用途：前端登录、写回后通知 CPA 重载
IMPORTER_UID / IMPORTER_GID建议容器运行身份。必须与 config.yaml 的属主一致，否则写回时 PermissionError
PROBE_PROXY可选探测用代理。复用 mihomo 时填 http://mihomo:7890
IMPORTER_LOG_LEVEL可选DEBUG / INFO（默认）/ WARNING。排错时用 DEBUG
IMPORTER_LOG_TO_FILE可选填 1 时日志同时写文件，便于事后排查
IMPORTER_MEMORY_LIMIT可选默认 1G。不要降到 512M：全量重探时会 OOM，表现为轮询突然无响应
MIHOMO_SECRET用代理时必填mihomo 的 RESTful API 鉴权密钥
MIHOMO_SUB_*用代理时必填机场订阅地址。等同凭据，绝不能提交
/opt/deploy/.env —— 与本工具相关的部分
# 登录与写回（CPA_MANAGEMENT_PASSWORD 必填）
CPA_MANAGEMENT_PASSWORD=填你的CPA后台密码
IMPORTER_TOKEN=

# 容器身份：必须和 config.yaml 的属主一致，否则写回会 PermissionError。
# 查属主：  stat -c '%u:%g' /opt/deploy/config.yaml
IMPORTER_UID=0
IMPORTER_GID=0

# 探测走代理（复用同栈的 mihomo 服务；不用代理就留空）
PROBE_PROXY=http://mihomo:7890

# 日志：排错期开 DEBUG + 落文件
IMPORTER_LOG_LEVEL=INFO
IMPORTER_LOG_TO_FILE=0

# 内存上限。低于 1G 在全量重探时会 OOM，表现为轮询突然卡住。
IMPORTER_MEMORY_LIMIT=1g

# 代理订阅（等同凭据，绝不要提交到任何仓库）
MIHOMO_SECRET=填一个随机长字符串
MIHOMO_SUB_MAIN=填你的机场订阅地址

4. 配置 docker-compose.yml

VPS 的 /opt/deploy/docker-compose.yml 里加入本服务。端口只绑回环，外部访问一律经 nginx。

/opt/deploy/docker-compose.yml —— upstream-importer 服务段
  upstream-importer:
    image: 你的DockerHub用户名/cpa-upstream-importer:latest
    pull_policy: always
    # 与 config.yaml 属主一致，否则写回 PermissionError
    user: "${IMPORTER_UID:-0}:${IMPORTER_GID:-0}"
    ports:
      # 只绑回环：外部访问经 nginx，不直接暴露
      - "127.0.0.1:8765:8765"
    environment:
      # 容器内 127.0.0.1 是容器自己，要用服务名
      CPA_UPSTREAM_URL: "http://cli-proxy-api:8317"
      CPA_MANAGEMENT_TOKEN: "${CPA_MANAGEMENT_PASSWORD}"
      IMPORTER_TOKEN: "${IMPORTER_TOKEN:-}"
      PROBE_PROXY: "${PROBE_PROXY:-http://mihomo:7890}"
      DRIFT_PROXY: "${PROBE_PROXY:-http://mihomo:7890}"
      IMPORTER_LOG_LEVEL: "${IMPORTER_LOG_LEVEL:-INFO}"
      IMPORTER_LOG_TO_FILE: "${IMPORTER_LOG_TO_FILE:-0}"
      IMPORTER_BACKUP_DIR: /backups
    volumes:
      # :Z 是 SELinux 标签，CentOS/RHEL enforcing 下必须加
      - ./config.yaml:/data/config.yaml:Z
      - importer-backups:/backups:Z
      - ./logs/upstream-importer:/var/log/upstream-importer:Z
    depends_on:
      cli-proxy-api:
        condition: service_started
      # 等代理就绪再起：否则启动头 40 秒走代理的探测会失败
      mihomo:
        condition: service_started
        required: false
    healthcheck:
      test: ["CMD","python3","-c",
             "import urllib.request;urllib.request.urlopen('http://127.0.0.1:8765/',timeout=5)"]
      interval: 60s
      timeout: 10s
      retries: 3
      start_period: 20s
    deploy:
      resources:
        limits:
          memory: "${IMPORTER_MEMORY_LIMIT:-1g}"
    cap_drop: [ALL]
    security_opt: ["no-new-privileges:true"]
    restart: unless-stopped

volumes:
  importer-backups:
备份卷必须是独立卷 IMPORTER_BACKUP_DIR 指向的目录如果和 config.yaml 同一个挂载点，容器可能写不进去，备份就静默失败了 —— 而你只会在需要回滚时才发现。用命名卷（上面的 importer-backups）最稳。

5. 配置 nginx.conf

三件事决定前端会不会报 Failed to fetch：超时够不够长、缓冲关没关、限速够不够宽。

/opt/deploy/nginx.conf —— http 段先定义限速区
http {
    # 分四档：登录严、轮询松、写回中、总量兜底
    limit_req_zone $binary_remote_addr zone=importer_auth:10m  rate=30r/m;
    limit_req_zone $binary_remote_addr zone=importer_all:10m   rate=240r/m;
    limit_req_zone $binary_remote_addr zone=importer_poll:10m  rate=20r/s;
    limit_req_zone $binary_remote_addr zone=importer_write:10m rate=60r/m;
    limit_conn_zone $binary_remote_addr zone=importer_conn:10m;
    # 回 429 而不是默认 503：前端能区分「你太快了」与「服务挂了」
    limit_req_status 429;

    client_max_body_size 100M;
}
/opt/deploy/nginx.conf —— server 段
server {
    listen 443 ssl http2;
    server_name 你的域名;

    # 证书路径按你的实际情况填
    ssl_certificate     /etc/nginx/certs/fullchain.pem;
    ssl_certificate_key /etc/nginx/certs/privkey.pem;

    limit_conn importer_conn 64;
    add_header Content-Security-Policy "default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'" always;
    add_header X-Content-Type-Options "nosniff" always;

    location / {
        # 900 秒：全量重探要跑很久。600 不够，会被掐断成 Failed to fetch
        proxy_connect_timeout 30;
        proxy_send_timeout   900;
        proxy_read_timeout   900;
        send_timeout         900;

        # 必须关缓冲：开着会把流式进度攒住，前端看起来像卡死
        proxy_buffering off;
        proxy_cache     off;

        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        limit_req zone=importer_all burst=120 nodelay;
        proxy_pass http://127.0.0.1:8765;
    }

    # 轮询单独放宽：它天然高频
    location /api/job      { limit_req zone=importer_poll burst=40 nodelay; proxy_buffering off; proxy_read_timeout 900; proxy_pass http://127.0.0.1:8765; }
    location /api/plan-status  { limit_req zone=importer_poll burst=40 nodelay; proxy_buffering off; proxy_read_timeout 900; proxy_pass http://127.0.0.1:8765; }
    location /api/apply-status { limit_req zone=importer_poll burst=40 nodelay; proxy_buffering off; proxy_read_timeout 900; proxy_pass http://127.0.0.1:8765; }
}
Cloudflare 橙云会在 nginx 之前掐断 Cloudflare 代理模式对回源有约 100 秒硬超时，nginx 配 900 秒也救不了 —— 超过就回 524，前端看到的就是 Failed to fetch。本项目已把定档改成异步任务来绕开它，但如果你还有别的长请求，把这个域名改成灰云（仅 DNS）最省事。

6. 配置代理（复用 mihomo）

很多中转站按出口 IP 拦截（Cloudflare 人机验证等）。本项目的镜像里自带 mihomo 二进制，可以直接起一个代理服务复用。

/opt/deploy/docker-compose.yml —— mihomo 服务段
  mihomo-init:
    image: 你的DockerHub用户名/cpa-upstream-importer:latest
    user: "0:0"
    entrypoint: ["/bin/sh","/app/mihomo-manager/bootstrap-mihomo.sh"]
    environment:
      MIHOMO_SECRET:   "${MIHOMO_SECRET}"
      MIHOMO_SUB_MAIN: "${MIHOMO_SUB_MAIN}"
      # 非空时强制重建配置；平时留空，按订阅指纹自动判断
      MIHOMO_FORCE_REBUILD: "${MIHOMO_FORCE_REBUILD:-}"
    volumes:
      - mihomo-config:/mihomo-config
    restart: "no"

  mihomo:
    image: 你的DockerHub用户名/cpa-upstream-importer:latest
    # 服务名就是容器间的 DNS 名，所以 PROBE_PROXY 填 http://mihomo:7890
    entrypoint: ["/usr/local/bin/mihomo","-d","/mihomo-config"]
    volumes:
      - mihomo-config:/mihomo-config
    depends_on:
      mihomo-init:
        condition: service_completed_successfully
    healthcheck:
      test: ["CMD","sh","/mihomo-config/healthcheck.sh"]
      interval: 60s
      timeout: 15s
      retries: 3
      start_period: 40s
    restart: unless-stopped

volumes:
  mihomo-config:
验证代理真的通了 下面这条应当输出 204。输出别的或卡住，就是订阅地址、密钥或网络有问题 —— 先修这里，再谈探测。
在 VPS 上执行
docker compose exec upstream-importer python3 -c "
import urllib.request
p='http://mihomo:7890'
o=urllib.request.build_opener(urllib.request.ProxyHandler({'http':p,'https':p}))
print(o.open('https://www.gstatic.com/generate_204',timeout=10).status)"

7. 部署与启动

  1. 确认 config.yaml 属主 容器身份和它不一致，写回时会 PermissionError。 
    stat -c 'IMPORTER_UID=%u' /opt/deploy/config.yaml >> /opt/deploy/.env
stat -c 'IMPORTER_GID=%g' /opt/deploy/config.yaml >> /opt/deploy/.env
  2. 先备份现有配置 工具自己会备份，但首次部署前手工留一份更踏实。 
    cp -a /opt/deploy/config.yaml /opt/deploy/config.yaml.bak-$(date +%Y%m%d-%H%M%S)
  3. 拉镜像并启动 
    cd /opt/deploy
docker compose pull upstream-importer mihomo
docker compose up -d upstream-importer mihomo
# up -d 立刻返回，但服务写 stdout 要一两秒，所以等 3 秒再看日志
sleep 3 && docker compose logs --tail=30 upstream-importer
  4. 确认健康 
    docker compose ps upstream-importer
curl -s -o /dev/null -w 'HTTP %{http_code}  耗时 %{time_total}s\n' http://127.0.0.1:8765/
    预期 HTTP 200，耗时 1 秒以内。
  5. 浏览器打开并登录 访问你的域名。登录用 IMPORTER_TOKEN，没设就用 CPA 后台管理密码。

8. 四个核心流程怎么用

① 投喂 → 写回（添加新账号）

  1. 粘贴账号 每行一条 URL,密钥。URL 带不带 /v1 都行，工具会按段自动补。
  2. 点「解析」 看清有几条有效、几条被判无效以及原因。
  3. 点「开始探测」 进度条按站推进。每个站四个段分别探，实时显示请求数。
  4. 核对方案 探完自动定档。重点看三列：段判定、模型勾选、priority。想改就直接改，改完会自动重算。
  5. 点「生成预览」 看 diff。这一步只读，不写盘。
  6. 点「确认写回」 写前备份 → 行级编辑 → 校验 → 通知 CPA 重载 → 验证上游。全过程有进度。

② 路由批量管理

按域名分组展示所有已配置的上游，支持筛选后批量改 priority、批量启用/停用、批量删除。解决的是 CPAMP 前端逐条点的问题。

同域名同优先级是硬规则 同一类型下，同一个域名的所有 Key 必须共享同一个 priority —— 它们互为备份，拆开会让调度退化成单点。批量面板会自动保持这条约束，手工改单条时也会提示。

③ 全局调优体检

读当前 config.yaml，按实际的站点分布给出可改项（重试次数、流式缓冲、冷却策略等），逐条说明依据，可一键写回。

④ 全量重探

把 config.yaml 里已有的站全部重新探测一遍，重新定档、重新生成参数。用于：站点状态变了、CPA 升级了、或者怀疑现有配置有问题。

全量重探很慢 几百个条目要跑十几到几十分钟。确保 nginx 超时 900 秒、Cloudflare 是灰云、内存上限 1G 以上。中途别关页面 —— 关了任务仍在后端跑，但进度看不到了。

9. 模型选择与定档规则

模型清单从哪来

四层优先级，前一层拿不到才用后一层：

层来源说明
1CPA 权威名录从 CPA 项目在线拉取，与 CPA 实际认识的模型集合同源
2本地 config.yaml站方特供型号只会在这层出现。需至少 2 个站在用才采纳，防手误外推
3本轮其他站目录同批探测中别的站返回的目录
4内置兜底前三层全空时的保底清单，会打 WARNING

勾选规则

  • 不勾 带 mini / flash / fast / lite / nano / haiku 的低档模型。
  • 全勾 同一代的所有变体。例如最新是 gpt-6 代，那么 gpt-6-astra 和 gpt-6-sol 都要勾上，不能只勾一个。
  • 段隔离 codex 段只收 gpt 系、gemini 段只收 gemini 系、claude 段只收 claude 系；openai-compatibility 段可以多族并存。
  • 档位择一 同一基名的算力档只留最高：裸名 > -high > -medium > -low。这样避免高低档同时出现。只有 -low 时保留它，否则该段会空。
  • 两代并存 最新代整体探不通、而次新代通时，两代都保留 —— 既不放弃最新，也不丢掉实际能用的。

定档（priority）

  • 同一类型 + 同一域名的所有 Key → 相同 priority（它们互为备份）。
  • 同一类型 + 不同域名 → 必须不同 priority，算出来相同也会做微调区分。
  • 健康分数参与排序：可调度比例与活跃比例共同决定名次，健康度高的 priority 更大。
  • 原本在配置里被停用、但本次探测证明可用的站，会重新启用并补齐全部参数。

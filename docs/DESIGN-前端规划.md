# 前端功能规划

写在动手之前。每一项都标注**为什么需要**（来自实际踩过的问题或代码里的既有缺口）、
**做多久**、**风险**。按「先补缺口、再加能力、最后打磨」排序 —— 不按「看起来酷」排序。

---

## 现状盘点（子代理探索 + 自查结论）

### 已有的三步流程

| 步 | panel | 做什么 |
|---|---|---|
| ① | `#p1` / `#pparse` | 粘贴 `url,key` → 解析（零请求） |
| ② | `#p2` | 探测，HTTP 轮询进度，事件流 |
| ③ | `#p3` | 判定与定档，勾选，生成方案 |
| ④ | `#p4` | diff 预览 → 确认写回 |

### 后端已支持而前端**没有入口**的能力

这几项是真缺口 —— 后端认这些参数，前端表达不了：

| 能力 | 后端位置 | 前端现状 |
|---|---|---|
| `overrides.headers` | `_api_plan` 认 | **无编辑入口**（只能整段接受探测结果） |
| `overrides.max_context_length` | 同上 | 无入口 |
| `by_score`（关掉试用期定档） | 同上 | 无入口 |
| `push.base` / `push.mgmt_key` | `_api_apply` 认 | 有输入框但藏得深 |
| 单站诊断 | `tools/diag-identity.py --url` | **只有 CLI** |

### 已有但信息未充分呈现

- `verdict.attempts[]` 每次尝试的 `combo` / `status` / `excerpt` —— 结果表只显示汇总，
  要看具体哪一档通了得展开事件流自己找
- `impacts[].shadowed_hosts` —— 有渲染但埋在展开区
- `profile_drift.betas_conditional` —— 后端返回 9 项，前端不显示

## 第一批：补真缺口（建议先做）

### 1.1 单站诊断面板

**为什么需要**：这是本轮对话反复撞到的问题 —— 想知道「anyrouter 要什么头」，
现在必须走完整条流水线（粘贴 → 探测 → 生成方案），或者去 VPS 上敲 CLI。
而这个动作与「批量导入」是**两个不同的意图**，不该复用同一条流水线。

**设计**：

```
┌─ 单站诊断 ──────────────────────────────── [收起] ─┐
│  url  [https://anyrouter.top          ]            │
│  key  [sk-xxxx                        ]            │
│  段    ○ 全部  ● claude  ○ codex  ○ gemini  ○ compat │
│        ☐ 同时探模型清单   ☐ 同时探上下文上限         │
│                                    [开始诊断]       │
├────────────────────────────────────────────────────┤
│  claude-api-key  ·  claude-opus-5                  │
│                                                     │
│  baseline          401  门禁   {"error":{"message"…  │
│  cc-min            401  门禁   …                     │
│  cc-std        ✓   200  通                          │
│                                                     │
│  ▸ 最小必需画像：cc-std                              │
│    需要这 4 个 header（点击复制为 YAML）：           │
│      user-agent: claude-cli/2.1.220 (external, cli) │
│      anthropic-beta: claude-code-20250219,…          │
│      x-app: cli                                     │
│      anthropic-version: 2023-06-01                  │
│                                                     │
│  ▸ 写进 config.yaml 的形态         [复制] [用它导入] │
└────────────────────────────────────────────────────┘
```

**关键设计决定**：

- **不生成方案、不写回**。它只回答「这个站要什么」。「用它导入」按钮把结果
  预填到步骤①，走正常流水线 —— 诊断与写回之间必须有人工确认这一跳。
- **默认只探一个段**。全四段是 25 档、约 25 次请求；单段 3-8 次。用户来这里
  通常已经知道要哪个段（截图那个场景就是 claude 段）。
- **可复制为 YAML**。诊断出来的 headers 直接能粘进 config.yaml，这是最短路径。
- 复用 `tools/diag-identity.py` 的判定逻辑，不另写一套。

**后端**：新增 `POST /api/diag`，参数 `{url, key, section, probe_models, probe_context}`，
返回每档的 attempt 列表 + 最小必需画像 + 渲染好的 YAML 片段。

**工作量**：后端 1.5h（复用 profiles.ladder + client.send）、前端 2h、测试 1h。**共 4.5h**

**风险**：低。只读，不碰 config.yaml。

### 1.2 headers 手工编辑

**为什么需要**：`_api_plan` 早就认 `overrides.headers`，但前端只能整段接受探测
结果。而两种情形都真实存在：

- 探测判「门禁」但你从别处知道正确的头（本轮 anyrouter 就是）
- 探测给出的头多了一项（比如漂移检测抓到的 `oauth-2025-04-20`）

**设计**：在步骤③每个段的行里加一个「编辑头」展开区：

```
  claude   ✓ 可用   cc-std   4 个 header        [编辑头 ▾]
  ┌──────────────────────────────────────────┐
  │ user-agent          [claude-cli/2.1.220…] │
  │ anthropic-beta      [claude-code-2025021…] │
  │ x-app               [cli               ]  │
  │ anthropic-version   [2023-06-01        ]  │
  │ [+ 加一行]                    [恢复探测值] │
  │                                            │
  │ ⚠ 改过头之后这一段的「已验证」不再成立 ——   │
  │   探测是用上面那套跑通的，改了就没测过了。  │
  └──────────────────────────────────────────┘
```

**关键设计决定**：

- 改动后**必须显式标注「未验证」**。这是最容易做错的地方：用户改了头，界面
  仍显示「✓ 可用」，会让人以为改后的配置也测过了。
- 「恢复探测值」一键回退。
- 空 key 或空 value 的行提交时丢弃（与 CPAMP 的 `buildHeaderObject` 一致，
  避免两边行为不同）。

**工作量**：前端 2h、测试 1h。**共 3h**

**风险**：中 —— 用户可能填出让 CPA 拒绝的头。缓解：写回前的 `validate()` 会挡
YAML 层面的问题，但语义错误（比如头名拼错）挡不住。所以那条警告必须显眼。

### 1.3 尝试明细可展开

**为什么需要**：`attempts[]` 里每次尝试的 `combo` / `status` / `excerpt` 后端都返回
了，但结果表只显示汇总。排障时要看「到底哪一档通的、别的档报什么」，现在得去
事件流里翻。

**设计**：结果表每行末尾加「N 次尝试 ▾」，展开显示一张小表：

```
  claude   ✗ 门禁   34 次请求                [34 次尝试 ▾]
  ┌─────────────────────────────────────────────────────┐
  │ 模型            画像              状态  类别  正文    │
  │ claude-opus-5   baseline          503   临时  {"err…  │
  │ claude-opus-5   retry1            503   临时  …       │
  │ claude-sonnet-5 baseline          404   死路  model_… │
  │ claude-opus-5   id:cc-min         403   门禁  only a… │
  │ …（可按状态/类别筛）                                  │
  └─────────────────────────────────────────────────────┘
```

**工作量**：前端 1.5h。**共 1.5h**

**风险**：低。纯展示，数据已在手上。

## 第二批：提升可用性

### 2.1 diff 的可读性改造

**为什么需要**：全量重探的 diff 是**整个文件**。175 个站、几千行，
现在是一整块 `<pre>`。人没法逐项确认，而「逐项确认」正是这个功能的安全前提。

**设计**：按段 → 按站分组折叠，每站一行摘要，点开看具体改动：

```
  gemini-api-key   16 个条目   3 处改动
    ▸ relay-a.example      priority 200 → 150
    ▸ relay-b.example      + headers（2 项）
    ▸ relay-c.example      models 4 → 6
    （其余 13 个无改动，已折叠）           [显示全部]

  claude-api-key   63 个条目   ⚠ 12 处改动   1 处删除
    ⚠ relay-f.example      整段删除 —— 探测判「余额」
    ▸ relay-g.example      priority 900 → 465，headers 变了
```

**关键设计决定**：

- **默认只显示有改动的**。无改动的折叠起来，但要显示计数（让人知道没漏掉）。
- **删除单独标红**。全量重写模式下「某站消失了」是最危险的改动，
  必须比 priority 变化更醒目。
- 提供「只看删除」「只看 headers 变化」这类筛选。

**工作量**：前端 4h、后端补结构化 diff 2h、测试 1.5h。**共 7.5h**

**风险**：中 —— 后端现在返回的是整文件文本，要改成结构化（按站分组的改动列表）。
这会动 `rebuild_config_full` 的返回值。

---

### 2.2 探测中的实时统计条

**为什么需要**：现在进度是 `42/78 · 成功 12 · 部分通 25 · 失败 5`，一行文字。
跑 5 分钟的任务只有这个反馈，不知道「卡在哪个站」「还要多久」。

**设计**：

```
  ████████████░░░░░░░░░░░░  42/78  (54%)   预计还需 2.1 分钟
  成功 12   部分通 25   失败 5        当前：api.example.com claude 段
  ⚠ 3 个站被限流（已自动降速）
```

**关键设计决定**：剩余时间用**已完成站的实测均值**推算，不用固定系数。
第一个站完成前不显示预计时间（宁可不显示，也不要显示一个瞎猜的数）。

**工作量**：前端 2h、后端进度事件补字段 0.5h。**共 2.5h**

**风险**：低。

---

### 2.3 窄屏与可访问性

**为什么需要**：当前无媒体查询、表格在窄屏会横向溢出；勾选框无 `aria-label`。
VPS 排障时用手机开这个页面是真实场景。

**设计**：

- 表格在 <900px 时转成卡片式（每条目一张卡，字段竖排）
- 所有勾选框补 `aria-label`，进度条补 `role="progressbar"` + `aria-valuenow`
- 事件流区域补 `aria-live="polite"`（屏幕阅读器能读到新事件）
- 焦点可见（当前 `:focus` 无样式，键盘操作看不出焦点在哪）

**工作量**：3h。

**风险**：低。

## 第三批：可以但不急

### 3.1 探测结果导出

导出 JSON / Markdown 报告，用于「贴给别人看」或留档。**1.5h**

### 3.2 历史记录

把每次探测的结果存 localStorage（**不含 key**），支持「上次那个站的结论是什么」。
**2.5h**，但要小心：localStorage 里存上游站名与判定结论，属于敏感信息，
需要显式的「清除历史」按钮。

### 3.3 画像梯可视化

把 25 档画像画成一张梯子图，标出每站命中哪一档。好看，但**信息价值有限** ——
真正要看的是「这个站要什么头」，那个 1.1 已经解决了。**4h**

---

## 明确不做的

| 想法 | 为什么不做 |
|---|---|
| WebSocket / SSE 替换轮询 | 现有轮询够用（1.5 秒间隔），换掉要动后端 Job 机制，收益是「进度更即时一点」，不值得 |
| 前端直连上游探测 | 浏览器有 CORS 限制，且会把 key 暴露给浏览器扩展。必须走后端 |
| 自动写回（免确认） | 违背整个工具的设计前提。config.yaml 是生产配置，写回必须人工确认 |
| 深色/浅色自动跟随系统 | 已有三套主题手动切换。自动跟随会让「我明明选了 midnight」失效 |

## 建议顺序与总量

| 批次 | 内容 | 累计工时 |
|---|---|---|
| 第一批 | 1.1 单站诊断 + 1.2 headers 编辑 + 1.3 尝试明细 | **9h** |
| 第二批 | 2.1 diff 改造 + 2.2 进度条 + 2.3 窄屏可访问性 | **+13h** |
| 第三批 | 3.1 导出 + 3.2 历史 + 3.3 梯子图 | **+8h** |

**我的建议：先做第一批**（9h）。三项都是补真缺口 —— 后端已支持而前端表达不了
的能力，或本轮对话实际撞到的问题。做完之后你用一阵，再定第二批做不做。

第二批里 **2.1 diff 改造** 单独值得优先：全量重探要真正能用，diff 必须能逐项
确认，而现在那一大块 `<pre>` 做不到。如果你打算尽快对 175 个真实站跑一次，
这一项应该提到第一批里。

---

## 需要你定的三件事

1. **先做哪一批？** 我建议第一批，或「第一批 + 2.1」。
2. **1.1 单站诊断的默认段**：默认「全部」还是「claude」？全部更省心但贵 8 倍。
3. **1.2 headers 编辑的严格程度**：要不要在提交前做头名校验（比如警告
   `anthropic_beta` 这种下划线拼错）？校验能挡住手滑，但也可能挡住我们没预料
   到的合法头。
